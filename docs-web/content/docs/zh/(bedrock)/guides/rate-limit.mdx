Bedrock 内置了一套官方限流组件，用于保护命令、任务和对外调用。它不感知 HTTP：服务从具名策略中消耗额度并拿到判定结果，被拒绝时在传输层意味着什么由适配层决定。整个子系统位于 `bedrock.contrib.rate_limit` 下。

## 快速开始

```python
from datetime import timedelta
from bedrock.contrib.rate_limit import RateLimitPolicy, rate_limit

LOGIN = RateLimitPolicy(name="idp.login", limit=5, period=timedelta(minutes=15))

decision = rate_limit.hit(LOGIN, f"{tenant_id}:{email}")
if not decision.allowed:
    raise LoginThrottledError(retry_after=decision.retry_after)  # your domain error

# After a successful login
rate_limit.reset(LOGIN, f"{tenant_id}:{email}")

# Async variants
decision = await rate_limit.ahit(LOGIN, key, cost=2)
await rate_limit.areset(LOGIN, key)
```

## 配置

内置后端为 Redis，要求 5 及以上版本。安装 extra 并指向你的 Redis：

```bash
uv add "bedrock-core[rate-limit-redis]"
```

```bash
RATE_LIMIT_BACKEND=redis                 # default
RATE_LIMIT_REDIS_URL=redis://redis:6379/0
RATE_LIMIT_REDIS_KEY_PREFIX=rate_limit:  # default
```

使用限流的模块都要在 `depends_on` 中加入 `bedrock.contrib.rate_limit`。该模块的 `ready` 钩子会调用 `rate_limit.configure()`，读取 `RATE_LIMIT_BACKEND`；如果模块从未执行 ready，第一次调用时也会这样做。未安装 extra 时，启动会以 `RateLimitBackendNotConfiguredError` 失败，错误信息会给出 `bedrock-core[rate-limit-redis]`。创建客户端不会建立连接：Redis 不可达时，要到第一次调用才会以 `RateLimitBackendError` 暴露出来。

`RATE_LIMIT_REDIS_*` 与缓存的 `CACHE_REDIS_*` 互相独立。配置相同的 URL 即可共用同一个 Redis，配置不同的 URL 则可以把限流数据与缓存数据隔离。

| 配置项 | 默认值 | 说明 |
|---------|---------|-------------|
| `RATE_LIMIT_REDIS_URL` | `redis://localhost:6379` | 连接 URL；URL 中带有数据库编号（`/2`）时优先于 `RATE_LIMIT_REDIS_DB` |
| `RATE_LIMIT_REDIS_DB` | `0` | 数据库编号，仅在 URL 未指定时生效 |
| `RATE_LIMIT_REDIS_PASSWORD` | 未设置 | 密码 |
| `RATE_LIMIT_REDIS_KEY_PREFIX` | `rate_limit:` | 所有 key 的前缀 |
| `RATE_LIMIT_REDIS_MAX_CONNECTIONS` | `50` | 每个客户端的连接池大小 |

也可以在代码中传入名称和配置：

```python
from bedrock.contrib.rate_limit import RedisRateLimitSettings, rate_limit

rate_limit.configure("redis", settings=RedisRateLimitSettings(url="redis://limits:6379/0"))
```

### 注册自定义后端

自定义后端需要实现 `RateLimitBackend` 协议，并对每个 key 原子地执行下文的令牌桶算法。在 `bootstrap.py:on_load` 中注册，再用 `RATE_LIMIT_BACKEND` 选中：

```python
from bedrock.contrib.rate_limit import register_backend

def on_load(**kwargs) -> None:
    register_backend("dynamo", DynamoRateLimitBackend)          # class or factory taking settings=
```

`register_backend_lazy(name, "module:attribute", install_requirement=...)` 会把导入推迟到该后端被选中时。在同一名称下再次注册同一个对象或同一路径不会产生任何效果；在已被占用的名称（包括 `redis`）下注册不同的后端会抛出 `DuplicateRegistrationError`。`configure()` 只检查成员名称，因此请为自定义后端编写契约测试。

## 语义

策略是一个按 GCRA 计算的令牌桶：

- 可以一次性用掉 `limit` 个单位；之后每隔 `period / limit` 恢复一个单位。该间隔向上取整到整微秒，因此桶的恢复速度不会快于配置值。
- `hit(policy, key, cost=1)` 在额度足够时消耗 `cost` 个单位（1 到 `limit` 之间的整数）。被拒绝的调用不消耗额度。
- `RateLimitDecision` 包含 `allowed`、`limit`、`remaining`（当前可用的单位数）、`retry_after`（再过多少秒这次的 cost 才能被放行；放行时为 `0.0`）和 `reset_after`（再过多少秒桶会回满）。
- Redis 在一条 Lua 脚本中使用服务端时钟完成每次判定，因此无论多少并发调用方或应用实例，都不会超出限额。

以 `limit=5, period=15 min` 为例：前 5 次立即放行，第 6 次被拒绝且 `retry_after ≈ 180`，之后每 3 分钟恢复一次机会。

策略应定义为模块常量。名称是每个存储 key 的一部分，因此同名的两个策略必须完全相同；使用参数不同的同名策略会抛出 `RateLimitPolicyConflictError`。

### Key

Key 在写入后端之前会用 BLAKE2b 哈希，邮箱、IP 地址或 API key 都不会被存储。多租户代码需要自己把租户放进 key：`f"{tenant_id}:{subject}"`。

### 放行还是拒绝

后端出错时，`hit()` 抛出 `RateLimitBackendError`。由每个调用点自行决定行为：

```python
from bedrock.contrib.rate_limit import RateLimitBackendError

try:
    decision = rate_limit.hit(LOGIN, key)
except RateLimitBackendError:
    raise ServiceUnavailableError()    # fail closed: protect credentials

try:
    allowed = rate_limit.hit(VENDOR_CALLS, provider_id).allowed
except RateLimitBackendError:
    allowed = True                     # fail open: keep serving
```

### 同步代码与异步 API

需要调用 `ahit()` 的同步代码应使用 `bedrock.run_async(...)`，而不是 `asyncio.run()`，这样异步客户端会留在关闭时使用的运行时事件循环上。

## RateLimitService API 参考

`rate_limit` 单例是一个 `RateLimitService` 实例。

| 方法 | 签名 | 说明 |
|--------|-----------|-------------|
| `hit` | `hit(policy, key, cost=1) -> RateLimitDecision` | 额度足够时消耗 |
| `ahit` | `async ahit(policy, key, cost=1) -> RateLimitDecision` | `hit` 的异步版本 |
| `reset` | `reset(policy, key) -> None` | 让桶回满 |
| `areset` | `async areset(policy, key) -> None` | `reset` 的异步版本 |
| `configure` | `configure(backend_name=None, settings=None) -> RateLimitBackend` | 选择后端；传 `None` 时读取 `RATE_LIMIT_BACKEND` |
| `get_backend` | `get_backend() -> RateLimitBackend` | 当前后端，未配置时惰性配置 |
| `close` / `aclose` | `close()`、`async aclose()` | 释放已创建的所有后端的同步 / 异步客户端 |
| `has_async_resources` | `has_async_resources() -> bool` | `aclose()` 是否还有需要释放的资源 |

## 异常层级

所有异常都继承自 `RateLimitError`（一个 `BedrockExc`）：

```python
from bedrock.contrib.rate_limit import (
    InvalidRateLimitArgumentError,       # empty key, or cost outside 1..limit
    InvalidRateLimitPolicyError,         # blank name, limit <= 0, period < 1 µs per unit
    RateLimitBackendError,               # backend failed; no connection details in the message
    RateLimitBackendNotConfiguredError,  # unknown backend or missing dependency
    RateLimitCloseError,                 # closing a backend failed
    RateLimitError,
    RateLimitPolicyConflictError,        # different policy under the same name
)
```

## 反模式

**不要在服务里把判定映射成 HTTP。** 返回或抛出携带 `retry_after` 的领域错误，由 HTTP 适配层转换为 429 和 `Retry-After` 响应头。

**不要意外地让多个租户共用一个桶。** 把租户放进 key。

**不要每次调用都新建策略。** 只定义一次；同名但参数不同会抛出 `RateLimitPolicyConflictError`。
