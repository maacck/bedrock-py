---
title: Provider
description: 以显式或延迟方式注册的具名 provider，按需创建并校验
---

`bedrock.provider.ProviderCatalog[P]` 把名称映射到同一能力的 provider。provider 是一个类或 factory 函数，它的返回值要实现协议 `P`。已导入的 provider 用显式注册；也可以注册延迟的 `module:attribute` 路径，只有被选中时才会导入。`create(name, **kwargs)` 构造并校验实例；`resolve(name)` 返回类或 factory，由应用自己构造。

## 选择 ClassRegistry 还是 provider

| 需求 | 使用 |
| --- | --- |
| 按名称查找**类**，并直接使用类本身（classmethod、按类型分派） | [`ClassRegistry`](./class-registry) |
| 每个实现都必须显式继承你的基类，并在注册时检查 | [`ClassRegistry`](./class-registry) |
| 按名称选择 provider，得到经协议校验的**实例** | `ProviderCatalog.create` |
| 由应用自己构造 provider（应用加载的凭据、位置参数、classmethod） | `ProviderCatalog.resolve` |
| factory 函数、只按结构实现协议的类，或带安装提示的可选 SDK | `ProviderCatalog` |

两者都支持延迟路径。只有 `ProviderCatalog` 接受 factory 函数、接受不继承协议的实现，并在导入失败时给出安装要求。

## 显式注册

```python
from typing import Protocol, runtime_checkable

from bedrock.provider import ProviderCatalog


@runtime_checkable
class Notifier(Protocol):
    def send(self, to: str, text: str) -> str: ...


class ConsoleNotifier:
    def __init__(self, prefix: str = "") -> None:
        self.prefix = prefix

    def send(self, to: str, text: str) -> str:
        return f"{self.prefix}{to}: {text}"


notifiers = ProviderCatalog[Notifier](protocol=Notifier)
notifiers.register("console", ConsoleNotifier)

notifier = notifiers.create("console", prefix="[dev] ")
assert notifier.send("ops", "deployed") == "[dev] ops: deployed"
```

`ConsoleNotifier` 没有继承 `Notifier`，只需要实现它。注册的对象按原样保留，包括在其他函数内部定义的类和函数。能注册对象，意味着它所在的模块已经被导入。

## 延迟注册

把协议放在轻量的 `base.py`，每个 provider 放在独立模块。内置 provider 在 catalog 上声明，其他模块在 `bootstrap.py:on_load` 中追加：

```python
# myapp/notify/service.py
from bedrock.provider import ProviderCatalog, ProviderSpec

from .base import Notifier

notifiers = ProviderCatalog[Notifier](
    protocol=Notifier,
    specs=(
        ProviderSpec("sms", "myapp.notify.providers.sms:SmsNotifier", install_requirement="myapp[sms]"),
    ),
)
```

```python
# myapp/notify/bootstrap.py
from .service import notifiers


def on_load() -> None:
    """Declare providers without importing them."""
    notifiers.register_lazy("email", "myapp.notify.providers.email:create_email_notifier")
```

注册时只检查路径语法。在 `resolve()` 或 `create()` 选中该名称之前不会导入任何东西；`has()` 和 `names()` 从不导入。父包的 `__init__.py` 不要导入 provider，因为 Python 导入子模块时会执行它们。不要用导入期的装饰器或 `__init_subclass__` 注册。

延迟 provider 无法导入时，错误信息会给出它的 `install_requirement`，例如 `Install 'myapp[sms]'.`

## create 还是 resolve

`create(name, **kwargs)` 用你传入的关键字参数调用 factory，并用 `isinstance(result, P)` 检查结果。catalog 从不读取配置，应用自己的配置由调用方传入：

```python
credentials = await credential_repo.aget(tenant_id)
notifier = notifiers.create("sms", api_key=credentials.api_key)
```

每次调用都会构造新实例。实例归调用方所有，包括关闭它持有的客户端。

`resolve(name)` 返回注册的类或 factory，但不调用它。需要类本身、位置参数或自定义构造逻辑时使用：

```python
sms_notifier_cls = notifiers.resolve("sms")
notifier = sms_notifier_cls.from_dsn(settings.sms_dsn)
```

`resolve()` 不做校验。用它构造出的对象不会被检查是否实现了 `P`，除非你自己检查。

## 接口

| 操作 | 结果 |
| --- | --- |
| `ProviderCatalog[P](protocol=P, specs=())` | 绑定到 `P` 的 catalog，用延迟 `ProviderSpec` 预置条目 |
| `register(name, factory)` | 记录已导入的类或 factory |
| `register_lazy(name, path, *, install_requirement=None)` | 记录路径而不导入 |
| `has(name)` | 检查是否已注册，而不是能否导入 |
| `names()` | 返回排序后的已注册名称 |
| `resolve(name)` | 返回类或 factory，延迟路径在首次使用时导入 |
| `create(name, **kwargs)` | 调用 factory，返回经过校验的实例 |
| `ProviderSpec(name, path, install_requirement=None)` | 不可变的延迟注册记录 |

名称是区分大小写的非空字符串。条目只能追加：不支持替换或删除。测试隔离请使用新的 catalog。

重复注册同一目标不会报错：显式模式下是同一个对象，延迟模式下是相同的路径和安装要求。同名下注册任何其他目标都会抛出 `ProviderConflictError`。同名的显式注册与延迟注册总是冲突，即使路径指向同一个对象，因为 catalog 不导入就无法比较两者。

## 校验

- `protocol` 必须能用于 `isinstance`：普通类，或带 `@runtime_checkable` 的 Protocol。
- `create()` 用 `isinstance` 检查结果。对 Protocol 而言，这只证明成员存在，不检查签名，也不检查方法是否为 async。行为请用静态类型检查和共享契约测试保证。
- 含 property 或其他非方法成员的 Protocol 不支持用 `issubclass` 检查类，而 factory 函数也不是类，所以校验发生在创建出的实例上。
- 延迟路径在导入之前无法做类型检查。

## 加载、并发与失败

解析出的延迟 factory 会被缓存，实例从不缓存。导入失败不会被缓存，之后再次调用会重试。注册和缓存发布是线程安全的；导入和 factory 调用都在 catalog 锁之外执行。首次导入是同步的，可能阻塞事件循环；有需要时，在 `ready()` 中预先解析已配置的 provider，再开始处理异步流量。

catalog 是进程内的。在一个 worker 中注册不会影响其他 worker。

所有错误都从 `bedrock.provider` 导出，继承 `ProviderError` / `BedrockExc`，并带有可读的 `detail`：

| 错误 | 含义 |
| --- | --- |
| `InvalidProviderSpecError` | 名称为空、路径格式错误、安装要求为空，或 factory 不可调用。同时也是 `InvalidRegisteredClassError` |
| `ProviderConflictError` | 该名称已被其他 provider 使用。同时也是 `DuplicateRegistrationError` |
| `ProviderNotFoundError` | 名称未注册；信息中列出可用名称 |
| `ProviderLoadError` | 延迟路径无法导入或解析，或 factory 抛出 `ImportError`；`__cause__` 保留原始异常 |
| `InvalidProviderError` | `create()` 得到的对象不是 `P` 的实例 |

factory 抛出的其他异常原样向上传播。

导入路径是可执行的配置。只接受来自可信代码或部署配置的路径，不要直接接受请求参数。请求只能选择已注册的名称。
