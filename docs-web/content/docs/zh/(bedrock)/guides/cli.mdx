Bedrock 提供了一个基于 Typer 的 CLI，用于管理模块、数据库迁移和应用生命周期。安装 `bedrock` 包时会自动安装该 CLI。

## 概览

```bash
bedrock [OPTIONS] COMMAND [ARGS]
```

### 全局选项

| 选项 | 简写 | 说明 |
|--------|-------|-------------|
| `--version` | `-v` | 显示 Bedrock 版本并退出 |
| `--help` | `-h` | 显示帮助信息并退出 |

### 命令组

| 组 | 用途 |
|-------|---------|
| `bedrock run` | 运行模块专属命令 |
| `bedrock app` | 检查和管理模块 |
| `bedrock manage` | 应用生命周期管理 |
| `bedrock db` | 数据库迁移操作 |

## 模块命令（`bedrock app`）

用于检查和管理 Bedrock 模块的命令。

### `bedrock app inspect`

校验模块的 manifest、可加载性和可选安装钩子的签名，但不执行任何安装逻辑。

```bash
bedrock app inspect <import_path>
```

**检查内容：**
1. `manifest.yaml` 结构和必填字段
2. 模块能否成功导入
3. Bootstrap 子模块是否存在
4. Models 子模块是否存在
5. 已存在的安装钩子是否接受必需的 `**kwargs` 签名；不会调用任何钩子

**示例：**

```bash
$ bedrock app inspect myapp.users

✓ Manifest for 'myapp.users' is valid.
✓ Module 'myapp.users' loads successfully.
✓ Bootstrap submodule is available.
! No models submodule found.
✓ Installation hooks for 'myapp.users' are valid (not executed).
```

`installation.py` 及其钩子均为可选项。请使用 `bedrock app install <import_path>` 执行安装生命周期钩子。

**退出码：**
- `0` — 所有检查通过
- `1` — 校验失败

### `bedrock app info`

显示模块的详细信息。

```bash
bedrock app info <import_path>
```

**示例：**

```bash
$ bedrock app info myapp.users

Dependencies myapp.core
             myapp.auth
Bootstrap    Yes
Models       Yes

```

### `bedrock app install`

安装 Bedrock 模块：确保数据库 schema 为最新，然后运行可选的安装生命周期钩子。

```bash
bedrock app install <import_path>
```

<Callout type="info">
`installation.py` 为可选项。存在 `install` 可调用对象时，Bedrock 会按 `pre_install` → `install` → `post_install` 的顺序执行。
</Callout>

---

### `bedrock app playbook`

读取模块 playbook 目录中的文档。

```bash
bedrock app playbook <module> [path]
```

不指定路径时，输出 `playbook/PLAYBOOK.md`。指定路径时，输出 `playbook/` 目录下的对应文件。Playbook 是面向 AI 的文档，存放在模块包内。详见 [Playbooks](./playbooks)。

**示例：**

```bash
# 读取主 playbook
bedrock app playbook myapp.auth

# 读取参考文件
bedrock app playbook myapp.auth references/architecture.md

# 读取代码示例
bedrock app playbook myapp.auth examples/login-flow.py
```

**安全性：** 会阻止路径遍历尝试（例如 `../`）。

## 数据库命令（`bedrock db`）

基于 Alembic 的数据库迁移命令。每条命令都接收一个应用导入路径，它既作为宿主应用，也作为迁移分支目标。

### `bedrock db revision`

创建新的迁移版本。

```bash
bedrock db revision <app_import_path> -m "<message>"
```

**选项：**

| 选项 | 简写 | 默认值 | 说明 |
|--------|-------|---------|-------------|
| `--message` | `-m` | 必填 | 该版本的简短描述 |
| `--autogenerate` | | `True` | 根据模型差异自动生成迁移 |
| `--no-autogenerate` | | | 禁用自动生成 |

**示例：**

```bash
# First revision (creates branch root)
bedrock db revision myapp.users -m "initial schema"

# Subsequent revision
bedrock db revision myapp.users -m "add email verification"

# Manual migration (no autogenerate)
bedrock db revision myapp.users -m "custom index" --no-autogenerate
```

**工作方式：**
- 首次调用会通过 `--head=base` 创建分支根节点
- 分支标签等于导入路径（例如 `myapp.users`）
- 后续调用会追加到 `<import_path>@head`

自动生成会在数据库侧和模型侧同时限制为目标 module 的表。普通 ORM 模型归定义它的 module，而不归导入它的 module。无 ORM 映射的 `Table` 必须声明 `info={"bedrock_module": "myapp.users"}`。归属缺失、冲突或 owner 未加载时，在写出 revision 前抛出 `MigrationError`，不会回退到全部表。参见[表归属](/docs/guides/database#表归属)。

数据库中已删除模型的旧表不会被自动认领到当前分支或自动删除。需要删除时，使用 `--no-autogenerate` 编写经过审查的显式迁移。手写迁移和历史升级／回滚执行不要求当前表归属快照。

---

### `bedrock db upgrade`

将数据库升级到目标版本。

```bash
bedrock db upgrade <app_import_path> [target]
```

**参数：**
- `target` — 目标版本（默认：`head`）

**目标格式：**

| 目标 | 说明 |
|--------|-------------|
| `head` | 升级到最新版本（默认） |
| `+1` | 向前升级一步 |
| `<revision_id>` | 升级到该应用分支中的指定版本 |

**示例：**

```bash
# Upgrade to latest
bedrock db upgrade myapp.users

# Upgrade one step
bedrock db upgrade myapp.users +1

# Upgrade to specific revision
bedrock db upgrade myapp.users abc123def456
```

**重要：** 只会升级指定应用的分支，其他分支不会受到影响。目标不属于该应用分支时（例如 `heads` 或其他应用的版本 ID）会报错。

升级和降级会获取迁移锁。PostgreSQL 使用 advisory lock，MySQL 和 MariaDB 使用 `GET_LOCK`，等待时间为 `DATABASE_MIGRATION_LOCK_TIMEOUT` 秒（默认 30）。SQLite 迁移不加锁，请只在一个进程中运行。超时会导致命令失败。

---

### `bedrock db downgrade`

将数据库回退到目标版本。

```bash
bedrock db downgrade <app_import_path> <target>
```

**目标格式：**

| 目标 | 说明 |
|--------|-------------|
| `base` | 移除该应用的全部版本（其他应用不受影响） |
| `-1` | 回退一步 |
| `<revision_id>` | 回退到该应用分支中的指定版本 |

只会移动指定应用的分支。目标不属于该分支时会报错。

**示例：**

```bash
# Downgrade one step
bedrock db downgrade myapp.users -1

# Downgrade to base
bedrock db downgrade myapp.users base
```

### `bedrock db check`

报告每个已加载迁移分支是否位于 head。该命令只读取数据库，不会修改它。

```bash
bedrock db check <app_import_path>
```

表格列出分支、已应用版本、脚本 head 和状态：

| 状态 | 含义 | 退出码 |
|-------|---------|-----------|
| `at-head` | 已应用版本与分支 head 一致 | 参与退出码 0 |
| `behind` | 已应用该分支上更早的版本 | 退出码 1 |
| `unknown` | 尚未应用版本、分支没有脚本，或已应用的版本不属于该分支 | 退出码 1 |

只有每个被报告的分支都是 `at-head` 时，进程才以 0 退出。

**示例：**

```bash
$ bedrock db check myapp.users

Branch        Current       Head          State
myapp.users   abc123def456  abc123def456  at-head
✓ All migration branches are at head.
```

### `bedrock db uninstall`

回滚目标应用已应用的版本，为移除该应用做好准备。

```bash
bedrock db uninstall <app_import_path>
```

**执行内容：**
1. 将目标应用已应用的版本回退到该分支的 base
2. 从 `alembic_version` 中移除该分支的条目
3. 核实迁移执行结果后，才移除模块

**先审查已有脚本。** 正确的分支标签并不限制 `downgrade()` 执行什么。首次安装可能只 stamp 了版本而没有运行其 `upgrade()`，卸载仍会执行其中的 `downgrade()`。归属过滤保护新的自动生成，不会修复旧污染脚本或拦截任意 SQL。卸载受影响应用前，先备份并遵循[已有迁移的安全处置](/docs/guides/database#已有迁移的安全处置)。

**示例：**

```bash
$ bedrock db uninstall myapp.users

✓ myapp.users downgraded to base. You can now remove it from INSTALLED_APPS.
```

## 应用管理（`bedrock manage`）

用于管理应用生命周期的命令。

### `bedrock manage install`

安装当前 Bedrock 应用。

```bash
bedrock manage [-A ROOT_MODULE] install [OPTIONS]
```

**选项：**

| 选项 | 简写 | 说明 |
|--------|-------|-------------|
| `--app` | | 安装指定的已加载模块（默认：所有已加载模块） |
| `--skip-migrations` | | 跳过数据库迁移 |

父级 `manage` 命令的 `-A ROOT_MODULE` 选项指定要加载的根模块；也可以设置 `BEDROCK_APP`。

**对每个模块会执行的操作：**

1. **数据库 schema** — 首次安装时创建表，若落后于 head 则执行升级
2. **安装前钩子** — 如果定义了 `installation.py:pre_install()` 就执行
3. **安装钩子** — 如果定义了 `installation.py:install()` 就执行
4. **安装后钩子** — 如果定义了 `installation.py:post_install()` 就执行

**示例：**

```bash
# Install all modules
bedrock manage install

# Install specific module
bedrock manage install --app myapp.users

# Skip migrations
bedrock manage install --skip-migrations
```

**示例输出：**

```bash
✓ Installing application...
Installing app: myapp.users 0.1.0
✓ Schema created (tables initialised and stamped at head).
Running pre-install hook for myapp.users...
Running post-install hook for myapp.users...
✓ Application installed successfully.
```

## 运行模块命令（`bedrock run`）

执行模块专属 CLI 命令。

```bash
bedrock run --app <root_module> <module> <command> [ARGS]
```

**选项：**

| 选项 | 简写 | 说明 |
|--------|-------|-------------|
| `--app` | `-a` | 要加载的模块（或设置 `BEDROCK_APP` 环境变量） |

### 模块命令的工作方式

模块可以在其 `commands.py` 文件中通过 Typer app 暴露 CLI 命令：

```python
# myapp/users/commands.py
import typer

app = typer.Typer(name="users", help="User management commands")

@app.command()
def create_user(name: str, email: str) -> None:
    """Create a new user."""
    ...

@app.command()
def list_users() -> None:
    """List all users."""
    ...
```

在 `manifest.yaml` 中注册：

```yaml
title: User Management
version: "0.1.0"
commands: commands:app
```

### 示例

```bash
# Run module command
bedrock run --app myapp.users myapp.users create-user --name Alice --email alice@example.com

# List available commands
bedrock run --app myapp.users myapp.users --help

# Use BEDROCK_APP environment variable
export BEDROCK_APP=myapp.users
bedrock run myapp.users create-user --name Bob --email bob@example.com
```

| 变量 | 说明 | 默认值 |

## 常见工作流

### 项目初始化

```bash
# 1. Install the application
bedrock manage install

# 2. Verify modules
bedrock app info myapp.users
bedrock app info myapp.products

# 3. Check database status
bedrock db current myapp.users
```

### 添加新的迁移

```bash
# 1. Create migration
bedrock db revision myapp.users -m "add phone field"

# 2. Review generated migration
# (check migrations/ directory)

# 3. Apply migration
bedrock db upgrade myapp.users

# 4. Verify
bedrock db current myapp.users
```

### 移除模块

```bash
# 1. Rollback migrations
bedrock db uninstall myapp.users

# 2. Remove from INSTALLED_APPS
# 3. Delete module code
```

### 调试模块问题

```bash
# 1. Validate manifest
bedrock app inspect myapp.users

# 2. Check module info
bedrock app info myapp.users

# 3. Read playbook (if available)
bedrock app playbook myapp.users
```
