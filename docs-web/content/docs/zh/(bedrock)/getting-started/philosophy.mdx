## 为什么会有 Bedrock

在 vibe coding 和 agentic coding 的时代，AI 助手已经成为强大的开发工具。然而，如果缺少清晰的约定和护栏，AI 生成的代码往往会出现可扩展性差、模式不一致、结构难以维护等问题。

为每个项目都编写 `AGENTS.md` 文件既繁琐又低效。Bedrock 正是为了解决这个问题而诞生——它提供了一个标准化的模块化开发框架，能够同时与人类开发者和 AI 编码助手顺畅协作。

## 起源

Bedrock 的设计灵感来自 Django 和 Odoo 的模块化开发方式。这两个框架都能让开发者专注于业务逻辑，而不必陷入框架内部实现的细节中。

不过，对于非 Web 应用场景来说，Django 偏重型的方式会显得有些过度设计。Bedrock 提供了一个更轻量的替代方案：既保留了模块化设计的优势，又保持精简并且与具体框架无关。

## 核心原则

### 1. 默认模块化

每个模块都是一个自包含单元，拥有自己的实体、服务、异常和生命周期钩子。模块之间通过显式依赖进行组织，从而避免代码耦合和结构失控。

```text
bedrock_app/
├── __init__.py
├── manifest.yaml
├── entities.py
├── service.py
├── exc.py
└── bootstrap.py
```

### 2. 约定优于配置

Bedrock 使用约定好的文件结构和命名规范来引导开发者。你不需要从零开始配置所有内容，只需遵循既定模式——其余工作交给框架处理。

这种方式同时对人类和 AI 都有好处：
- 人类开发者可以减少在样板决策上花费的时间
- 由于架构清晰明确，AI 助手能够生成更准确的代码

### 3. 生命周期管理

模块可以定义生命周期钩子，在初始化和关闭过程中的合适时机执行。这能确保正确的加载顺序、资源清理和集成初始化。

### 4. 显式依赖

模块会在 `manifest.yaml` 中声明自己的依赖。运行时会校验依赖图、检测循环依赖，并计算出确定性的加载顺序。没有魔法，也没有导入时副作用。

### 5. 面向 AI 的架构

Bedrock 从一开始就是为与 AI 编码助手协作而设计的：

- **可预测的结构** —— AI 可以判断代码应该放在哪里
- **清晰的边界** —— AI 知道每一层应该包含什么
- **由 Manifest 驱动** —— AI 无需扫描代码也能理解模块关系
- **基于约定** —— AI 会遵循既有模式，而不是自行发明模式

## 设计哲学

### 与业务松耦合

Bedrock 有意将自己与业务逻辑的耦合降到最低。核心框架提供的是模式和基础设施——它不会规定你的应用必须做什么。

功能和能力应通过扩展模块添加，而不是直接修改 Bedrock 核心。这样既能保持框架稳定，也能让你的业务逻辑保持独立。

### 一个框架，多种用例

Bedrock 并不局限于 Web 应用。相同的模块化模式同样适用于：

- Web 应用（FastAPI，或任何 HTTP 框架）
- CLI 工具
- 后台 worker
- AI agents 和 assistants
- 内部工具

无论运行时环境是什么，模块系统都能提供一致的结构。

## 愿景

Bedrock 希望成为构建可维护、可扩展 Python 应用的基础——无论你是独立开发者、团队成员，还是正在编写代码的 AI 助手。

通过建立清晰的约定并提供健壮的模块系统，Bedrock 能帮助你：

- 以更少的样板代码更快交付
- 在项目增长时持续保持代码质量
- 更高效地与 AI 工具协作
- 将业务逻辑与框架关注点分离
