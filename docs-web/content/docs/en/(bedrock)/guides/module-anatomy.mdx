## Standard Module Structure

A module is an importable Python package with a `manifest.yaml` at its root.

```files
bedrock_app/
├── playbook/
│   └──PLAYBOOK.md
├── __init__.py
├── manifest.yaml
├── models.py
├── entities.py
├── schemas.py
├── service.py
├── exc.py
└── bootstrap.py
```

## File Descriptions

| File | Required | Description |
|------|----------|-------------|
| `__init__.py` | Yes | Standard Python Module File |
| `manifest.yaml` | Yes | Module declaration and metadata |
| `models.py` | No | Data models and persistence |
| `entities.py` | No | Business entities for internal data flow |
| `schemas.py` | No | API input/output schemas (request/response DTOs) |
| `service.py` | No | Business logic layer |
| `exc.py` | No | Module-specific exceptions |
| `bootstrap.py` | No | Lifecycle hooks |
| `commands.py` | No | Module Typer app |


## Module Manifest

Bedrock loads module metadata from `manifest.yaml`.

```yaml
title: My Bedrock App
description: An app building on Bedrock
version: 0.1.0
depends_on:
  - users
commands: "commands:app"
```

### Key Fields

- `title`: (required) Human-friendly display name used in logging and error messages
- `description`: (optional) Short description of the module
- `version`: (optional, default `"unknown"`) Module version string
- `depends_on`: (optional, default `[]`) Ordered list of import paths this module depends on
- `commands`: (optional) Relative import path to a Typer app, e.g. `"commands:app"`

## File Descriptions with Examples

### `manifest.yaml`

The manifest declares the module's identity, version, dependencies, and optional CLI entry point. This is the only **required** file beyond `__init__.py`.

```yaml
title: inventory
description: Product inventory management
version: 0.1.0
depends_on:
  - products
  - warehouse
commands: "commands:app"
```

### `entities.py`

Pydantic models for business domain entities. These represent data that flows within the service layer — not tied to any specific API contract. Entities can also be used as output when a dedicated response schema is not needed.

```python
from pydantic import BaseModel


class Product(BaseModel):
    """Business entity representing a product."""

    id: int
    name: str
    sku: str
    price: int
```

### `schemas.py`

Pydantic models for API input/output contracts. Use schemas when you need dedicated request validation or response serialization that differs from your business entities. This file is optional — simple modules can use entities directly.

```python
from pydantic import BaseModel, Field


class ProductCreateRequest(BaseModel):
    """Input schema for creating a product."""

    name: str = Field(..., min_length=1, max_length=100)
    sku: str = Field(..., pattern=r"^[A-Z0-9\-]+$")
    price: int = Field(..., ge=0, description="Price in cents")


class ProductResponse(BaseModel):
    """Output schema for product queries."""

    id: int
    name: str
    sku: str
    price: int
```

### `service.py`

Business logic layer. Services receive data as Pydantic entities or primitives — never HTTP request objects or ORM instances directly.

```python
from bedrock.database import db

from .schemas import ProductCreateRequest, ProductResponse
from .models import Product


class InventoryService:
    """Inventory business operations."""

    def create_product(self, data: ProductCreateRequest) -> ProductResponse:
        """Create a new product in the inventory."""
        product = Product(name=data.name, sku=data.sku, price=data.price)
        db.session.add(product)
        db.session.commit()
        return ProductResponse(
            id=product.id, name=product.name, sku=product.sku, price=product.price
        )

    def get_product(self, product_id: int) -> ProductResponse | None:
        """Retrieve a product by ID."""
        product = db.session.query(Product).get(product_id)
        if product is None:
            return None
        return ProductResponse(
            id=product.id, name=product.name, sku=product.sku, price=product.price
        )
```

### `exc.py`

Module-specific exceptions. All exceptions extend `BedrockExc` and declare a `detail` class attribute for consistent error reporting.

```python
from bedrock.exc import BedrockExc


class ProductNotFoundError(BedrockExc):
    """Raised when a requested product does not exist."""

    detail = "Product not found"


class DuplicateSkuError(BedrockExc):
    """Raised when a product SKU already exists."""

    detail = "A product with this SKU already exists"
```

### `bootstrap.py`

Lifecycle hooks are called by the registry at specific stages. The registry invokes them with keyword arguments, injecting supported parameters by name.

```python
from bedrock.module.registry import ModuleRegistry
from bedrock.module.entities import AppConfig


def on_load(*, registry: ModuleRegistry, app: AppConfig, container, hooks) -> None:
    """Called when this module is first loaded.

    Parameters are injected by name:
    - registry: the ModuleRegistry instance
    - app: this module's AppConfig
    - container: the global DI container (bedrock.di.container)
    - hooks: the global HookRegistry (bedrock.hooks.hooks)
    """
    print(f"Module '{app.name}' loaded (v{app.manifest.version})")


def ready(*, registry: ModuleRegistry, app: AppConfig) -> None:
    """Called after ALL modules have been loaded.

    Use for cross-module setup that depends on other modules being available.
    """
    print(f"Module '{app.name}' ready")


def on_shutdown(*, registry: ModuleRegistry, app: AppConfig) -> None:
    """Called during graceful shutdown (reverse dependency order).

    Use for cleanup: closing connections, flushing buffers, releasing resources.
    """
    print(f"Module '{app.name}' shutting down")
```

### `commands.py`

Optional Typer app that provides module-specific CLI commands. Referenced in the manifest as `commands: "commands:app"`.

```python
import typer

app = typer.Typer(help="Inventory management commands")


@app.command()
def sync(source: str = typer.Argument(..., help="External source to sync from")):
    """Sync inventory from an external source."""
    typer.echo(f"Syncing inventory from {source}...")


@app.command()
def audit():
    """Run an inventory audit check."""
    typer.echo("Running audit...")
```

## Manifest Field Reference

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `title` | `str` | Yes | — | Human-friendly display name for logging and errors |
| `description` | `str \| None` | No | `None` | Short description of the module |
| `version` | `str` | No | `"unknown"` | Module version string (semver recommended) |
| `depends_on` | `list[str]` | No | `[]` | Ordered list of module import paths this module depends on |
| `commands` | `str \| None` | No | `None` | Relative import path to a Typer app, e.g. `"commands:app"` |

The manifest is validated by the `ModuleManifest` Pydantic model at load time. Invalid or missing required fields raise an `InvalidManifestError`.

## Lifecycle Hooks

Bedrock modules participate in a three-phase lifecycle managed by the `ModuleRegistry`. Hooks are optional functions defined in `bootstrap.py`.

### Hook Signatures

Hooks may declare keyword parameters by name. The registry inspects the signature and injects matching arguments automatically:

```python
def hook_name(*, registry, app, container, hooks) -> None: ...
```

| Parameter | Type | Description |
|-----------|------|-------------|
| `registry` | `ModuleRegistry` | The registry managing all modules |
| `app` | `AppConfig` | The current module's config (manifest, package info, state) |
| `container` | `Container` | The global DI container (`bedrock.di.container`) |
| `hooks` | `HookRegistry` | The global hook registry (`bedrock.hooks.hooks`) |

For dedicated API details, see [Dependency Injection](/docs/guides/di) and
[Hook System](/docs/guides/hooks).

Declare at least one supported parameter, or `**kwargs` to receive all four. Unsupported required parameters and required positional-only parameters are rejected. `registry.get()` and `registry.all()` require the registry to be ready, so use `is_installed()` or `list_installed()` during module hooks instead.

### Call Order

```
install("module_a")
  ├── Install dependencies (recursive)
  ├── on_load(*, registry, app)     ← per-module, in dependency order
  └── Signal: module_loaded

mark_ready()
  ├── ready(*, registry, app)       ← per-module, in install order
  ├── Signal: module_ready          ← per-module
  └── Signal: registry_ready        ← once, after all modules

shutdown()
  ├── on_shutdown(*, registry, app) ← per-module, REVERSE install order
  ├── Signal: module_shutdown       ← per-module
  └── Signal: registry_shutdown     ← once, after all modules
```

### Hook Descriptions

| Hook | Phase | Description |
|------|-------|-------------|
| `on_load` | Install | Module just loaded. Register signal receivers, validate config, set up module state. |
| `ready` | Ready | All requested modules are loaded, but other modules' `ready` hooks may not have run and registry queries requiring readiness are unavailable. |
| `on_shutdown` | Shutdown | Graceful teardown. Close connections, flush buffers, release resources. |

### Failure Semantics

The registry keeps its state consistent when a lifecycle step fails, so startup can be retried and shutdown always tries to release everything.

- **Install is failure-atomic.** If `install()` (or the install phase of `populate()`) fails, every module introduced by that call is removed from the registry and from install order. Modules installed before the call are never removed. Introduced modules that had already finished `on_load` are unwound best-effort in reverse install order: `module_shutdown` is emitted only if their `on_shutdown` hook succeeds. If cleanup fails, `ModuleStartupRollbackError` (a `ModuleLifecycleError`) is raised; its `failures` hold the original failure first, then the cleanup failures.
- **Rollback cannot grow the registry.** Cleanup hooks and signal receivers must not introduce new modules through `install()` or `populate()` during rollback. Such attempts raise `ModuleLifecycleError` before loading the new module; uncaught errors are included in the rollback failures.
- **Readiness is tracked per module.** Modules move through `loading → loaded → ready → shutdown`, though a loaded module can shut down before becoming ready. `AppConfig.lifecycle_state` is read-only (assigning to it raises `AttributeError`, and passing it to the constructor raises `ValidationError`); only the registry changes it, through `AppConfig.transition_to()`, which rejects invalid transitions. A module installed after the registry became ready stays `loaded` until `mark_ready()` runs again, while `registry.ready` stays `True`, so check a module's `lifecycle_state` rather than reading `registry.ready` as "every installed module is ready". A failed `ready` hook leaves already-readied modules ready; retrying `mark_ready()` (or `populate()` with the same paths) skips them. A `module_ready` receiver failure occurs after the module becomes ready, so that module's hook and signal are not retried.
- **Shutdown attempts every module.** `shutdown()` attempts each unfinished module in reverse install order and aggregates hook and `module_shutdown` receiver failures in a `ModuleLifecycleError`; it does not emit `registry_shutdown` on that call. A failed hook is retried, but a failed `module_shutdown` receiver is not: the module was already marked shut down. A subsequent call can emit `registry_shutdown` after the remaining modules finish.
- **Registry notifications can be retried.** If a `registry_ready` or `registry_shutdown` receiver raises, retry `mark_ready()` or `shutdown()` to resend the notification without repeating completed module hooks. A failed ready notification resets `registry.ready` to `False`, so `bedrock.setup()` can also retry. The registry remains queryable inside ready receivers. Notification retries resend the signal, so receivers that already succeeded may run again and must be retry-safe.
- **`mark_ready()` and `shutdown()` are not re-entrant.** Calling either from a hook or a signal receiver while one of them is running raises `ModuleLifecycleError` instead of re-running hooks. Trigger shutdown outside the hook (for example, set a flag and call `shutdown()` from your main loop) rather than from `on_shutdown` or `ready`.
- **`shutdown()` and `mark_ready()` are rejected while a module installs.** An `on_load` hook, a `module_loaded` receiver, or a rollback hook that calls either raises `ModuleLifecycleError` ("Cannot call shutdown() while install() is running"). The registry is only partly installed at that point, so the call is rejected rather than run or deferred until the installation finishes. To abort an installation, raise an error from the hook: the install rolls back and every module that had loaded is unwound. `on_load` hooks and `module_loaded` receivers may still call `install()` for further modules.
- **New modules cannot be installed while `mark_ready()` or `shutdown()` runs.** Calling `install()` (or `populate()`) for a module that is not installed yet from a `ready` or `on_shutdown` hook, or from a `module_ready`, `registry_ready`, `module_shutdown`, or `registry_shutdown` receiver, raises `ModuleLifecycleError` before anything is loaded, so the registry is unchanged. Readiness is decided for a fixed set of modules, and a module installed halfway through would be `loaded` in a registry that already reports `ready`. Install the module before `mark_ready()`, or call `install()` and then `mark_ready()` again, which readies only the new module. Installing an already installed module is always a no-op.
- **Aggregated failures are attributed.** Entries in an aggregate error's `failures` name the module and step, and its `__cause__` is an `ExceptionGroup`. Other errors, including `module_ready` receiver errors, can propagate directly.

### Async Lifecycle

Every lifecycle operation has a synchronous entrypoint and an `a`-prefixed asynchronous one. They run the same implementation, so the failure semantics above apply to both.

| Sync | Async | Process level |
|------|-------|---------------|
| `install()` | `ainstall()` | |
| `populate()` | `apopulate()` | `bedrock.setup()` / `await bedrock.asetup()` |
| `mark_ready()` | `amark_ready()` | |
| `shutdown()` | `ashutdown()` | `bedrock.shutdown()` / `await bedrock.ashutdown()` |

Hooks and signal receivers keep their names and may be plain functions or `async def`. A plain function that returns an awaitable has it awaited as well:

```python
async def on_load(*, registry, app) -> None:
    app_state.client = await open_client()


async def on_shutdown(*, registry, app) -> None:
    await app_state.client.aclose()
```

- **Async entrypoints** await async hooks on the running loop and run plain hooks in a worker thread (like `hooks.acall` and `Signal.asend`). Mixed sync and async graphs start in dependency order and shut down in reverse order.
- **Sync entrypoints** call plain hooks directly. They run async hooks on a private event loop that stays open until every module has shut down, so a client opened by `on_load` is closed by `on_shutdown` on the same loop. This only works when the calling thread has no running event loop.
- **Inside a running loop**, a sync entrypoint that needs to run async work raises `ModuleAsyncRequiredError` (a `ModuleLifecycleError`) naming the async entrypoint to use. It never starts a nested loop or leaves a coroutine unawaited. `mark_ready()` and `shutdown()` check for coroutine hooks before running any, so they change nothing; `install()` rolls back like any other install failure. A registry whose hooks are all plain functions keeps working from sync entrypoints inside a loop.
- **Use one family end to end.** An async client is bound to the loop that opened it, so start and stop through the same entrypoint family (`asetup()` with `ashutdown()`, or `setup()` with `shutdown()`). Mixing them is unsupported for loop-bound clients.
- **Operations are serialized across `await`.** The guard does not hold a thread lock. Unrelated tasks and threads wait for the running operation; a call from a hook, a receiver, or a task or `to_thread` worker they started is rejected as described above. A synchronous call from a different task on the thread that owns the running operation raises instead of deadlocking. If an async operation is cancelled, `CancelledError` propagates, every module stays in a valid state, an interrupted install still rolls back, and calling `amark_ready()` or `ashutdown()` again resumes with the modules that have not finished, so hooks must be safe to run again. A blocking synchronous hook or receiver that already started in a worker thread cannot be forced to stop, so the cancellation is raised only after it returns: cancelling may wait for an in-flight hook, repeated cancellation does not shorten the wait, and neither the rollback, the next operation nor the release of the operation overlaps a running worker. An awaitable returned by a plain hook after cancellation is released instead of awaited. A coroutine hook is cancelled directly. The rollback of a failed or cancelled install is the exception: cancelling during it does not abort a cleanup hook or skip a module. Every introduced module is still unwound in reverse order while the operation stays held, then `CancelledError` is raised, with the install error that started the rollback as its `__cause__`; cleanup failures are logged and added to the `CancelledError` as notes. If a cleanup hook itself raises `CancelledError` or `KeyboardInterrupt`, the unwind stops and that module and the modules it depends on stay registered in their current state, so `shutdown()` can finish them. The check that guarantees nothing changes before a `ModuleAsyncRequiredError` covers coroutine hooks only, not plain hooks that return an awaitable.

#### Shutting down process infrastructure

The database is process infrastructure, not a module. `bedrock.shutdown()` and `bedrock.ashutdown()` stop every module first and then release an initialized database: `db.close()` for the sync engine and `db.aclose()` for the async engine, each only if it exists. This also happens when a module hook failed, and a database failure is added to the same aggregate error. Nothing is initialized or rebuilt if the database was never used. `bedrock.shutdown()` called inside a running loop while an async engine exists raises `ModuleAsyncRequiredError` before anything changes; use `await bedrock.ashutdown()`. A cancelled `ashutdown()` does not release the database; call it again.

A module that owns both sync and async clients releases both. Keep `on_shutdown` a plain function that closes the sync client and returns the awaitable that closes the async one, so shutdown completes only after the async close does. `bedrock.contrib.cache` and `bedrock.contrib.metric` do this.

### Signals

Each lifecycle transition emits a signal that external code can observe:

| Signal | Emitted After | Payload |
|--------|---------------|---------|
| `module_loaded` | `on_load` hook | `registry`, `module`, `config` |
| `module_ready` | `ready` hook | `registry`, `module`, `config` |
| `module_shutdown` | `on_shutdown` hook | `registry`, `module`, `config` |
| `registry_ready` | All modules ready | `registry`, `config` |
| `registry_shutdown` | All modules shut down | `registry`, `config` |

## Minimal Module Example

A complete, copy-pasteable module with all required files. This example uses `entities.py` only — add `schemas.py` when you need dedicated API input/output contracts.

```files
my_module/
├── __init__.py
├── manifest.yaml
├── entities.py
├── service.py
├── exc.py
└── bootstrap.py
```

**`my_module/__init__.py`**

```python
"""My Module — a minimal Bedrock module."""
```

**`my_module/manifest.yaml`**

```yaml
title: My Module
description: A minimal example module
version: 0.1.0
```

**`my_module/entities.py`**

```python
from pydantic import BaseModel


class Greeting(BaseModel):
    """A simple greeting entity."""

    message: str
    recipient: str
```

**`my_module/service.py`**

```python
from .entities import Greeting


class GreetingService:
    """Service that produces greetings."""

    def greet(self, name: str) -> Greeting:
        """Create a greeting for the given name."""
        return Greeting(message=f"Hello, {name}!", recipient=name)
```

**`my_module/exc.py`**

```python
from bedrock.exc import BedrockExc


class GreetingError(BedrockExc):
    """Raised when a greeting cannot be produced."""

    detail = "Failed to produce greeting"
```

**`my_module/bootstrap.py`**

```python
from bedrock.module.registry import ModuleRegistry
from bedrock.module.entities import AppConfig


def on_load(*, registry: ModuleRegistry, app: AppConfig) -> None:
    """Module loaded — initialize state."""
    pass


def ready(*, registry: ModuleRegistry, app: AppConfig) -> None:
    """All modules loaded — perform cross-module setup."""
    pass


def on_shutdown(*, registry: ModuleRegistry, app: AppConfig) -> None:
    """Shutdown — clean up resources."""
    pass
```

**Usage:**

```python
from bedrock.module.registry import apps

# Install and ready the module
apps.populate(["my_module"])

# Access the module
module = apps.get("my_module")
print(module.manifest.title)  # "My Module"
```

## Loader Flow

The registry installs explicit import paths; it does not scan a module root:

1. Import each requested package, validate its manifest, and import optional `bootstrap` and `models` modules.
2. Recursively install dependencies in manifest order, detecting cycles.
3. Register each module, call `on_load`, and emit `module_loaded`.
4. `populate()` then calls `mark_ready()` to run ready hooks and emit readiness signals.

Installation rollback removes registry entries and calls shutdown hooks for loaded modules; it cannot automatically undo arbitrary side effects such as DI or hook registrations.

## Where Does My Code Belong?

Use these rules to decide which file a piece of code belongs in:

- If it touches `Request`, `Response`, or HTTP status codes → **API layer** (routes/controllers)
- If it imports `sqlalchemy` → **Data layer** (`models.py`)
- If it imports `pydantic` for input/output shapes → **Schemas** (`schemas.py`) or **Entities** (`entities.py`)
- If it contains conditional logic, calculations, or orchestration → **Logic layer** (`service.py`)
- If it runs once at startup → **Lifecycle hooks** (`bootstrap.py`)
