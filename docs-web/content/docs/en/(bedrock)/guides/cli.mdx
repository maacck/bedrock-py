Bedrock provides a Typer-based CLI for managing modules, database migrations, and running module commands. The CLI is installed automatically with the `bedrock` package.

## Overview

```bash
bedrock [OPTIONS] COMMAND [ARGS]
```

### Global Options

| Option | Short | Description |
|--------|-------|-------------|
| `--version` | `-v` | Show Bedrock version and exit |
| `--help` | `-h` | Show help message and exit |

### Command Groups

| Group | Purpose |
|-------|---------|
| `bedrock run` | Run a module's own commands |
| `bedrock app` | Read: `inspect`, `info`, `playbook`. Write: `install` |
| `bedrock db` | Status (read-only): `heads`, `current`, `check`, `history`. Write: `revision`, `upgrade`, `downgrade`, `adopt`, `init-ledger` |

Only `run`, `app`, and `db` exist. The former `bedrock manage` group and `bedrock db uninstall` were removed.

## Module Commands (`bedrock app`)

Commands for inspecting and managing Bedrock modules.

### `bedrock app inspect`

Validate a module's manifest, loadability, and optional installation-hook signatures without executing installation logic.

```bash
bedrock app inspect <import_path>
```

**What it checks:**
1. `manifest.yaml` structure and required fields
2. Module can be imported successfully
3. Bootstrap submodule exists
4. Models submodule exists
5. Present installation hooks accept the required `**kwargs` signature; no hook is invoked

**Example:**

```bash
$ bedrock app inspect myapp.users

✓ Manifest for 'myapp.users' is valid.
✓ Module 'myapp.users' loads successfully.
✓ Bootstrap submodule is available.
! No models submodule found.
✓ Installation hooks for 'myapp.users' are valid (not executed).
```

`installation.py` and its hooks are optional. Use `bedrock app install <import_path>` to run the installation lifecycle hooks.

**Exit codes:**
- `0` — All checks passed
- `1` — Validation failed

### `bedrock app install`

Install a Bedrock module: ensure its database schema is current, then run its optional installation lifecycle hooks.

```bash
bedrock app install <TARGET> [--root ROOT] [--with-dependencies] [--skip-migrations]
```

| Option | Description |
|--------|-------------|
| `--root ROOT` | Root module to load. Selects the load context only; it never widens what is installed. Without it, TARGET is loaded as the root |
| `--with-dependencies` | Also install TARGET's `depends_on` closure, once each, in dependency order, then TARGET |
| `--skip-migrations` | Skip the schema step only; installation hooks still run |

By default only TARGET is installed. Installing a module that depends on others does not run those dependencies' hooks unless you pass `--with-dependencies`; the root and sibling modules are never installed implicitly.

**Scope.** `--with-dependencies` controls which modules' *schema step and hooks* run. It is separate from the migration closure: whenever the schema step runs for a module, Bedrock applies that module's migrations together with the migrations of other modules they depend on (the same scope as `bedrock db upgrade`), so a dependency's tables can be created even without `--with-dependencies`, but its `installation.py` hooks run only with it.

**Hooks are not tracked.** Bedrock does not record that a module was installed. Every run repeats `pre_install` → `install` → `post_install` for each installed module, so hooks must be idempotent.

```bash
# Only myapp.users
bedrock app install myapp.users

# myapp.users and its dependencies, loaded through the root myapp
bedrock app install myapp.users --root myapp --with-dependencies

# Run hooks only
bedrock app install myapp.users --skip-migrations
```

<Callout type="info">
`installation.py` is optional. When its `install` callable is present, Bedrock runs `pre_install` → `install` → `post_install`.
</Callout>

### `bedrock app playbook`

Read documentation from a module's playbook directory.

```bash
bedrock app playbook <module> [path]
```

Without a path, prints `playbook/PLAYBOOK.md`. With a path, prints the specified file from the `playbook/` directory. Playbooks are AI-readable documentation stored inside the module package. See [Playbooks](./playbooks) for details.

**Examples:**

```bash
# Read the main playbook
bedrock app playbook myapp.auth

# Read a reference file
bedrock app playbook myapp.auth references/architecture.md

# Read code examples
bedrock app playbook myapp.auth examples/login-flow.py
```

**Security:** Path traversal attempts (e.g., `../`) are blocked.

## Database Commands (`bedrock db`)

Database migration commands backed by Bedrock's own version table (`bedrock_migrations`, keyed by `(app, revision)`); Alembic is used only as a library to execute and autogenerate scripts. Each command takes an app import path that serves as both the host app and migration target. A database created by an earlier version must be adopted once with `bedrock db adopt` first.

### `bedrock db squash`

```bash
bedrock db squash prepare orders --from 0002_add --through 0004_finalize --root shop --out ./candidate
# To supply reviewed data operations or custom SQL instead:
bedrock db squash prepare orders --from 0002_add --through 0004_finalize --root shop --out ./manual --script ./replacement.py
# Ordinary deployment needs nothing more: `bedrock db upgrade` reconciles complete ranges first.
# Optional preview, or manual handover/recovery:
bedrock db squash apply orders 0004_finalize --root shop
bedrock db squash apply orders 0004_finalize --root shop --apply
```

Repeat `--root` for all project roots. Preparation keeps the last full revision ID unless you pass e.g. `--rename 0002_feature`; apply then takes that new ID. Any reference to a retired revision outside the range blocks the operation. Partly applied ranges are refused by upgrade and apply alike; reach the old end on the bridge release first. See the database guide for rollout and recovery.

### `bedrock db revision`

Create a new migration revision.

```bash
bedrock db revision <app_import_path> -m "<message>"
```

**Options:**

| Option | Short | Default | Description |
|--------|-------|---------|-------------|
| `--message` | `-m` | Required | Short description for the revision |
| `--autogenerate` | | `True` | Autogenerate migration from model diff |
| `--no-autogenerate` | | | Disable autogeneration |

**Examples:**

```bash
# First revision (creates 0001_initial)
bedrock db revision myapp.users -m "initial schema"

# Subsequent revision
bedrock db revision myapp.users -m "add email verification"

# Manual migration (no autogenerate)
bedrock db revision myapp.users -m "custom index" --no-autogenerate
```

**How it works:**
- The new revision is named `<number>_<slug>`, e.g. `0001_initial`: the module's highest number plus one, and a slug of the message
- The first call creates a root revision (`down_revision = None`); later calls revise the module's single head
- Dependencies on other modules are written automatically as qualified `app:revision` entries in `depends_on`, and must be direct manifest dependencies
- With autogeneration, the app must be at head (`bedrock db upgrade <app>` first); an unapplied revision makes generation fail without writing a file. `--no-autogenerate` skips this check but still requires a single head

Autogeneration compares only the target module's tables on both the database and model sides. Ordinary ORM models are owned by their defining module, not by modules importing them. Unmapped `Table` objects require `info={"bedrock_module": "myapp.users"}`. Missing, conflicting, or unloaded owners raise `MigrationError` before a revision is written; there is no all-tables fallback. See [Table Ownership](/docs/guides/database#table-ownership).

The generated file is a reviewable draft: review and commit it. Runtime ordering uses only the committed `depends_on` graph, never foreign keys.

A database table whose model was removed is not automatically assigned to this module or dropped. Use `--no-autogenerate` and write a reviewed explicit migration for such a drop. Handwritten migrations and historical upgrade/downgrade execution do not require a current ownership snapshot.

### `bedrock db upgrade`

Upgrade database to a target revision.

```bash
bedrock db upgrade <app_import_path> [target]
```

**Arguments:**
- `target` — Revision target (default: `head`)

**Target formats:**

| Target | Description |
|--------|-------------|
| `head` | Upgrade to latest revision (default) |
| `+1` | Upgrade one step |
| `<revision_name>` | Upgrade to a specific full revision name of this app (e.g. `0002_add_email`) |

**Examples:**

```bash
# Upgrade to latest
bedrock db upgrade myapp.users

# Upgrade one step
bedrock db upgrade myapp.users +1

# Upgrade to specific revision
bedrock db upgrade myapp.users 0002_add_email
```

**Important:** Only the specified app's migrations run, together with the migrations they depend on in other modules. Unrelated modules and later revisions of a dependency are untouched. A target that is not a revision name of this app, such as `heads` or another app's revision name, fails with an error. Each executed step is printed as `app:revision`, or `Nothing to do.`.

Upgrade and downgrade take a migration lock. PostgreSQL uses an advisory lock, MySQL and MariaDB use `GET_LOCK`, and the wait is `DATABASE_MIGRATION_LOCK_TIMEOUT` seconds (default 30). SQLite migrations are not locked; run them from one process. A timeout fails the command.

The CLI records migrations in one ledger, `bedrock_migrations` by default. Set `DATABASE_MIGRATION_VERSION_TABLE` (lowercase simple SQL identifier, at most 57 characters) to use another name; there is no CLI flag for it. Never rename the table to switch ledgers. See [Custom Version Table](/docs/guides/database#custom-version-table-and-independent-module-sets).

### `bedrock db downgrade`

Downgrade database to a target revision.

```bash
bedrock db downgrade <app_import_path> <target>
```

**Target formats:**

| Target | Description |
|--------|-------------|
| `base` | Remove all of this app's revisions (other apps untouched) |
| `-1` | Downgrade one step |
| `<revision_name>` | Undo the app's applied descendants of this full revision name (the revision itself stays) |

Only the specified app's revisions move; a target that is not a revision name of this app fails with an error. If applied migrations of other modules depend on what would be undone, the command fails and changes nothing. Pass `--cascade` to undo those dependents first; dependents whose modules are not loaded are always an error, so add `--load <app>` for each one. Baseline rows imported by `adopt` cannot be undone. `downgrade <app> base` is the CLI way to remove a module's schema; there is no `bedrock db uninstall` command. Review the module's existing `downgrade()` scripts first (see [existing migration safety](/docs/guides/database#existing-migration-safety)); ownership filtering protects new autogeneration, not old scripts or arbitrary SQL.

**Options:**

| Option | Description |
|--------|-------------|
| `--cascade` | Also roll back applied migrations of loaded modules that depend on the ones being removed |
| `--load <app>` | Also load this module so its applied migrations are known; repeatable |

**Examples:**
```bash
# Downgrade one step (`--` is required before a negative target)
bedrock db downgrade myapp.users -- -1

# Downgrade to base
bedrock db downgrade myapp.users base

# Roll back a module that other loaded modules depend on
bedrock db downgrade myapp.users base --load myapp.orders --cascade
```

### `bedrock db check`

Report whether each loaded module's migrations are at head. The command reads the database and does not change it.

```bash
bedrock db check <app_import_path>
```

The table lists the module, the applied revisions, the script heads, and a state:

| State | Meaning | Exit code |
|-------|---------|-----------|
| `at-head` | Applied revisions match the module's heads | Contributes to exit 0 |
| `behind` | An older revision of the module is applied | Exit 1 |
| `unknown` | Nothing is applied, the module has no scripts, or an applied revision has no script | Exit 1 |

The process exits 0 only when every reported module is `at-head`.

**Example:**

```bash
$ bedrock db check myapp.users

Branch        Current       Head          State
myapp.users   abc123def456  abc123def456  at-head
✓ All migration branches are at head.
```

### `bedrock db adopt`

Import a database created by an earlier Bedrock version (migrations recorded in Alembic's `alembic_version`) into `bedrock_migrations`.

```bash
bedrock db adopt <app_import_path> [<app_import_path> ...]
```

Load every module that has migrations; each old head must belong to exactly one of them. Until you run this once, every other migration command refuses to run on such a database.

**What it does:**
1. Resolves each old head through the deployment's own revision graph. A missing, ambiguous, or unresolvable head writes nothing.
2. Writes one `baseline` row for every revision up to those heads, then publishes the table atomically. If `bedrock_migrations` already exists it reports the database as initialised and does not import again.
3. Leaves `alembic_version` untouched as an audit snapshot. No migration script is executed.

Baseline rows assume the schema is already in place and are protected: a downgrade or cascade that would undo one fails before any DDL runs. Back up first and follow [Adopting an Existing Database](/docs/guides/database#adopting-an-existing-database).

**Example:**

```bash
$ bedrock db adopt myapp.users myapp.orders

✓ Imported 3 baseline migration(s). No scripts were executed.
```

### `bedrock db init-ledger`

Create the configured ledger for a new, independent module registry inside a database whose core modules were already adopted.

```bash
bedrock db init-ledger <root> [<root> ...] --adopted-ledger <source-name>
```

| Option | Required | Description |
|--------|----------|-------------|
| `--adopted-ledger` | Yes | Name of the already adopted source ledger (for example `bedrock_migrations`); read-only |

Set `DATABASE_MIGRATION_VERSION_TABLE` to the new target; use this command only for modules without existing history or schema.

Creates only an empty target ledger; does not copy rows or run migration scripts. Back up first and rehearse on a restored copy.

**Expected failures** (nothing is written): missing legacy table; source not a valid adopted ledger or lacking evidence for the old heads; source rows already exist for a loaded module; a table owned by a loaded module's models already exists; the target ledger or a source/target staging table already exists.

```bash
$ bedrock db init-ledger myapp.billing --adopted-ledger bedrock_migrations
```

## Running Module Commands (`bedrock run`)

Execute a module's own CLI commands.

```bash
bedrock run --app <root_module> <module> <command> [ARGS]
```

`--app` loads the root module and its dependency closure. `<module>` is the loaded module whose commands you want, and `<command>` is one of its Typer commands. Business commands are only reachable through `run`; there is no `bedrock manage` group.

**Options:**

| Option | Short | Description |
|--------|-------|-------------|
| `--app` | `-a` | Root module to load (or set `BEDROCK_APP`) |

### How Module Commands Work

Modules can expose CLI commands via a Typer app in their `commands.py` file:

```python
# myapp/users/commands.py
import typer

app = typer.Typer(name="users", help="User management commands")

@app.command()
def create_user(name: str, email: str) -> None:
    """Create a new user."""
    ...

@app.command()
def list_users() -> None:
    """List all users."""
    ...
```

Register in `manifest.yaml`:

```yaml
title: User Management
version: "0.1.0"
commands: commands:app
```

### Examples

```bash
# Run module command
bedrock run --app myapp myapp.users create-user --name Alice --email alice@example.com

# List available commands
bedrock run --app myapp myapp.users --help

# Use BEDROCK_APP environment variable
export BEDROCK_APP=myapp
bedrock run myapp.users create-user --name Bob --email bob@example.com
```

## Common Workflows

### Initial Project Setup

```bash
# 1. Install the root module and everything it depends on
bedrock app install myapp --with-dependencies

# 2. Verify modules
bedrock app info myapp.users
bedrock app info myapp.products

# 3. Check database status
bedrock db current myapp.users
```

### Adding a New Migration

```bash
# 1. Create migration
bedrock db revision myapp.users -m "add phone field"

# 2. Review generated migration
# (check migrations/ directory)

# 3. Apply migration
bedrock db upgrade myapp.users

# 4. Verify
bedrock db current myapp.users
```

### Removing a Module

```bash
# 1. Roll back its migrations (add --load <dependent> --cascade if other modules depend on it)
bedrock db downgrade myapp.users base

# 2. Remove it from your root module's depends_on / INSTALLED_APPS
# 3. Delete module code
```

### Debugging Module Issues

```bash
# 1. Validate manifest
bedrock app inspect myapp.users

# 2. Check module info
bedrock app info myapp.users

# 3. Read playbook (if available)
bedrock app playbook myapp.users
```
