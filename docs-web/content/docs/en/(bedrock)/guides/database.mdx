Bedrock ships with a SQLAlchemy 2.0 database layer that handles engine setup, context-local sessions, declarative models, and Alembic migrations. The whole subsystem lives under `bedrock.database`.

## Quick Start

Define a model, initialize the database, and start querying:

```python
from bedrock.database import db, BedrockModel
from sqlalchemy import Column, String, Integer

class Product(BedrockModel):
    __tablename__ = "products"

    id = Column(Integer, primary_key=True)
    name = Column(String(100), nullable=False)

# Initialize once at process start
db.init()

# Use a transaction scope (and unbind the session on exit)
with db.session_scope() as session:
    product = Product(name="Widget")
    session.add(product)
    session.flush()

    # Query back
    all_products = session.query(Product).all()
```

That's the core loop. The rest of this page covers configuration, the full API, and advanced patterns.

## Configuration

Database settings use environment variables with the `DATABASE_` prefix. `DbSettings` is a Pydantic `BaseSettings` subclass, so it reads from the environment automatically.

### Environment Variables

| Variable | Type | Default | Description |
|----------|------|---------|-------------|
| `DATABASE_TYPE` | `str` | `"sqlite"` | Database dialect (`sqlite`, `postgresql`, `mysql`) |
| `DATABASE_DRIVER` | `str` | `"pysqlite"` | DBAPI driver (`pysqlite`, `psycopg2`, `pymysql`) |
| `DATABASE_HOST` | `str \| None` | `None` | Database host (required for non-SQLite) |
| `DATABASE_PORT` | `int \| None` | `None` | Database port (required for non-SQLite) |
| `DATABASE_USERNAME` | `str \| None` | `None` | Database username |
| `DATABASE_PASSWORD` | `SecretStr \| None` | `None` | Database password. Omitted from `repr` and validation errors. |
| `DATABASE_ASYNC_DRIVER` | `str \| None` | `None` | Async DBAPI driver (`aiosqlite`, `asyncpg`, `psycopg`, `asyncmy`, `aiomysql`) |
| `DATABASE_MAX_CONNECTIONS` | `int` | `10` | Per-process connection ceiling, including overflow |
| `DATABASE_POOL_TIMEOUT` | `int` | `30` | Seconds to wait for a connection |
| `DATABASE_POOL_SIZE` | `int` | `10` | Steady-state pool size. Must be at least 1. |
| `DATABASE_POOL_RECYCLE` | `int` | `1800` | Seconds before recycling a connection |
| `DATABASE_MIGRATION_LOCK_TIMEOUT` | `float` | `30` | Seconds to wait for the migration lock. `0` does not wait. |
| `DATABASE_MIGRATION_VERSION_TABLE` | `str` | `"bedrock_migrations"` | Table that records applied migrations. Lowercase simple SQL identifier, at most 57 characters. See [Custom Version Table](#custom-version-table-and-independent-module-sets). |
| `DATABASE_SCHEMA` | `str` | `"bedrock.db"` | Database name or file path |

`MAX_CONNECTIONS` is the total number of connections one process may check out. PostgreSQL and MySQL engines receive `pool_size`, `pool_timeout`, `pool_recycle`, and `max_overflow = MAX_CONNECTIONS - POOL_SIZE`. `MAX_CONNECTIONS` must be greater than or equal to `POOL_SIZE`. A smaller value raises `DatabaseConfigurationError` and the message names both settings. `POOL_SIZE` below 1 also raises `DatabaseConfigurationError`, because SQLAlchemy treats a pool size of 0 as unlimited and would ignore the ceiling. SQLite engines ignore the pool settings.

The defaults (`POOL_SIZE=10`, `MAX_CONNECTIONS=10`) cap a process at 10 connections. Those defaults previously left SQLAlchemy's implicit overflow of 10 in place, so the engine allowed 20. Raise `DATABASE_MAX_CONNECTIONS` above `DATABASE_POOL_SIZE` when a deployment needs that extra capacity.

`PASSWORD` is a Pydantic `SecretStr`. A plain string is accepted and stored as a secret. `repr(settings)` and validation errors do not contain the password or the rendered URL. The URL is built with `sqlalchemy.engine.URL.create`, so `@`, `:`, `/`, and `%` in the username or password round-trip. Read the secret with `settings.PASSWORD.get_secret_value()` only where the connection is opened.

### Programmatic Configuration

Pass a `DbSettings` instance directly to `db.init()`:

```python
from bedrock.database import db, DbSettings

settings = DbSettings(
    TYPE="postgresql",
    DRIVER="psycopg2",
    HOST="localhost",
    PORT=5432,
    USERNAME="admin",
    PASSWORD="secret",
    SCHEMA="myapp",
)

db.init(settings=settings)
```

You can also override the connection URL entirely:

```python
db.init(url="postgresql+psycopg2://admin:secret@localhost:5432/myapp")
```

## DatabaseManager

The `db` singleton is a `DatabaseManager` instance. It owns the engine, session factory, and settings. All access goes through this object.

### API Reference

| Method / Property | Signature | Description |
|-------------------|-----------|-------------|
| `db.init()` | `init(url: str \| None = None, settings: DbSettings \| None = None)` | Initialize engine and session factory. Call once at process start. |
| `db.engine` | `property → Engine` | The SQLAlchemy engine. Raises `DatabaseNotConfiguredError` if not initialized. |
| `db.session` | `property → Session` | The session bound to the current context. Raises `SessionNotBoundError` when none is bound. |
| `db.session_factory` | `property → SessionFactory` | The underlying session factory. |
| `db.settings` | `property → DbSettings` | The resolved database settings. |
| `db.set_session(session)` | `set_session(session: Session)` | Bind an existing session to the current execution context. |
| `db.clear_session()` | `clear_session()` | Close and unbind the current context-local session. |
| `db.session_scope()` | `contextmanager → Session` | Transactional scope with auto commit/rollback. Binds to context. Also usable as a decorator. |
| `db.independent_session()` | `contextmanager → Session` | Isolated transaction that does not bind to context. |
| `db.aengine` | `property → AsyncEngine` | Async engine for the URL resolved by `init()`, with only the driver swapped for `DATABASE_ASYNC_DRIVER`. |
| `db.asession` | `property → AsyncSession` | The async session bound to the current context. Separate context variable from `db.session`. Raises `SessionNotBoundError` when none is bound. |
| `db.asession_scope()` | `async context manager → AsyncSession` | Async transactional scope with the same commit, rollback, and nesting rules as `session_scope()`. Also usable as a decorator on `async def`. |
| `db.aindependent_session()` | `async context manager → AsyncSession` | Async transaction that does not bind `db.asession`. |
| `db.close()` | `close()` | Dispose the sync engine. Leaves a built async engine usable. Safe to call twice. `init()` works again afterwards. |
| `db.aclose()` | `async aclose()` | Dispose the async engine. Leaves the sync engine usable. Safe to call twice. |

### Error Handling

Accessing `db.engine`, `db.session`, or `db.settings` before calling `db.init()` raises `DatabaseNotConfiguredError`. Always initialize the database before using any of these properties.

Reading `db.session` or `db.asession` when no session is bound to the current context raises `SessionNotBoundError` (a `BedrockExc`). Nothing is created implicitly: open a scope at the entry point.

## Session Management

Bedrock uses context-local sessions backed by a `ContextVar`. New async tasks inherit their creator's context, including any bound session; clear or establish separate bindings at task and request boundaries rather than sharing a session concurrently.

### How It Works

The `SessionFactory` wraps SQLAlchemy's `sessionmaker`. `db.session` returns the session stored in the `ContextVar` and never creates one. Something at the entry point binds it:

| Entry point | Binds the session with |
|-------------|------------------------|
| Script, CLI command, custom worker, WebSocket handler, startup hook | `with db.session_scope():` or `@db.session_scope()` |
| FastAPI HTTP request | `DbSessionMiddleware` / `AsyncDbSessionMiddleware` from `bedrock-fastapi` |
| Test | `with db.session_scope():` in the test; the `db_session` fixture from `bedrock.testing` rolls it back |
| Session managed by another framework | `db.set_session(...)` |

Services read `db.session` and commit; they never open a scope themselves:

```python
from bedrock.database import db

# service.py
def create_product(name: str) -> None:
    db.session.add(Product(name=name))
    db.session.commit()

# entry point
db.init()
with db.session_scope():
    create_product("Widget")

create_product("Gadget")  # raises SessionNotBoundError: no scope is open
```

### Transaction Scopes with `session_scope()`

The recommended way to manage transactions is `session_scope()`. It creates a new session, binds it to the current context, and guarantees commit on clean exit or rollback on exception:

```python
from bedrock.database import db

db.init()

# Automatic commit on success
with db.session_scope() as session:
    product = Product(name="Widget")
    session.add(product)
    # Session commits automatically when block exits cleanly

# Automatic rollback on exception
try:
    with db.session_scope() as session:
        session.add(Product(name="Gadget"))
        raise ValueError("Something went wrong")  # Rolls back
except ValueError:
    pass  # "Gadget" was never persisted
```

**Key behaviors:**
- Binds the session to `ContextVar` so `db.session` works inside the block
- Commits on clean exit, rolls back on any exception (including `BaseException`)
- Always closes the session and resets the `ContextVar` on exit
- Raises `SessionAlreadyBoundError` (a `BedrockExc` that is also a `RuntimeError`) if called while a session is already bound (prevents nesting)

### Decorating Entry Points

`session_scope()` and `asession_scope()` also work as decorators. Every call opens a new scope, so each invocation gets its own session and transaction. The decorator can be applied before `db.init()`, because the database is only used when the function is called:

```python
from bedrock.database import db

@db.session_scope()
def import_products(path: str) -> None:
    for name in read_names(path):
        db.session.add(Product(name=name))

@db.asession_scope()
async def sync_inventory() -> None:
    await refresh_stock(db.asession)
```

Note the parentheses: `@db.session_scope()`, not `@db.session_scope`. The function's return value passes through unchanged. Do not decorate a function that is called while a session is already bound, such as a service called from a request: the nested scope raises `SessionAlreadyBoundError`.

### Independent Sessions with `independent_session()`

For side-effect writes that must not interfere with the current transaction, use `independent_session()`. It creates an isolated session that does **not** bind to the `ContextVar`:

```python
from bedrock.database import db

db.init()

with db.session_scope() as session:
    # Main transaction
    order = Order(total=100)
    session.add(order)

    # Write an audit log in a separate transaction
    with db.independent_session() as audit_session:
        audit_log = AuditLog(action="order_started")
        audit_session.add(audit_log)
        # Commits independently — does not affect the outer session

    # db.session still returns the outer session
    assert db.session is session
```

**Use cases for `independent_session()`:**
- Audit logging (must persist even if the main transaction rolls back)
- Event publishing with an independent transaction (a transactional outbox must instead share the main transaction)
- Reads that must not see uncommitted data from the caller
- Background tasks that need their own transaction lifecycle

### Async Sessions

Async services use the same scoping rules with an `a` prefix. Set `DATABASE_ASYNC_DRIVER` and install the extra that provides that driver:

| Driver | Install |
|--------|---------|
| `aiosqlite` | `pip install 'bedrock-core[async-sqlite]'` |
| `asyncpg` | `pip install 'bedrock-core[async-postgresql]'` |
| `asyncmy` | `pip install 'bedrock-core[async-mysql]'` |
| `psycopg`, `aiomysql` | Install the driver package itself (`pip install psycopg` / `pip install aiomysql`) |

`db.asession_scope()` commits on a clean exit, rolls back on any exception, and refuses to nest when an async session is already bound. `db.aindependent_session()` does not bind `db.asession`. The async session uses its own context variable, so a sync session in the same task stays in place. A missing driver package raises `DatabaseConfigurationError` and names the extra to install.

```python
from bedrock.database import db, DbSettings

db.init(settings=DbSettings(ASYNC_DRIVER="aiosqlite"))

async with db.asession_scope() as session:
    session.add(Product(name="Widget"))

await db.aclose()
db.close()
```

### Closing Engines

Call `db.close()` for the synchronous engine and `await db.aclose()` for the asynchronous engine. If both were built, call both. Calling either method again does nothing further to that side. After `close()`, synchronous access raises `DatabaseNotConfiguredError` until `db.init()`, while an async engine that was already built still works. After `aclose()`, the synchronous engine still works, and the next async access builds a new async engine when synchronous configuration remains. These methods do not shut down the module registry. To stop a process, call `bedrock.shutdown()` (or `await bedrock.ashutdown()`): it stops every module and then calls `db.close()` and, if an async engine exists, `db.aclose()` once each, so both pools are released after every module hook, even when one failed. A never-initialized database is left alone. Inside a running event loop with an async engine, use `await bedrock.ashutdown()`; `bedrock.shutdown()` raises `ModuleAsyncRequiredError` before changing anything.

`db.init()` disposes the previous synchronous engine. It does not synchronously dispose an async engine that has already opened a connection: that close runs outside the event loop and fails with `MissingGreenlet`. Await `db.aclose()` before `db.init()` when that async engine should be closed. An async engine that has not opened a connection is disposed during `init()`.

### Binding an External Session

When working with frameworks that manage their own sessions (like FastAPI's dependency injection), you can bind an existing session:

For FastAPI, prefer the [DB session middlewares](/docs/integrations/fastapi#database-sessions) from the FastAPI integration.

```python
from bedrock.database import db

# Bind a session from an external source
db.set_session(framework_session)
try:
    product = db.session.query(Product).first()
finally:
    db.clear_session()  # Closes the session, then unbinds it
```

## BedrockModel

All Bedrock models extend `BedrockModel`, which combines SQLAlchemy's `DeclarativeBase` with a `CrudMixin` for common operations.

### Built-in Methods

| Method / Property | Description |
|-------------------|-------------|
| `.dict()` | Returns a dictionary of all column values |
| `.update(**kwargs)` | Sets attributes from keyword arguments |
| `.delete()` | Deletes the instance from its session |
| `.verbose_name` | Returns the class name as a human-readable label |
| `.__repr__()` | Returns `<ClassName #id>` format |

### Example

```python
from bedrock.database import BedrockModel
from sqlalchemy import Column, String, Integer

class Product(BedrockModel):
    __tablename__ = "products"
    __filterable_fields__ = ["name", "price"]

    id = Column(Integer, primary_key=True)
    name = Column(String(100), nullable=False)
    price = Column(Integer, default=0)

# Create and use
product = Product(name="Widget", price=999)
product.dict()  # {"id": None, "name": "Widget", "price": 999}

# Update attributes
product.update(price=1499)

# Delete (must be attached to a session)
session.add(product)
session.commit()
product.delete()
session.commit()
```

### Default Values

BedrockModel listens for the `init` event and applies column defaults before the constructor finishes. Callable defaults are invoked with the instance as an argument; explicitly supplied keyword arguments take precedence.

## Query Builder

The `search_filter_sort_paginate` function builds queries with filtering, sorting, pagination, and automatic joins. It returns a dictionary with `items`, `total`, and `page_info`.

### Filterable Fields

`filter_specs`, `sort_key`, and `group_by` usually come from the client, so they may only reference fields the model exposes. Primary keys are always allowed; every other column, hybrid, association proxy, or relationship must be listed in `__filterable_fields__`:

```python
class Order(BedrockModel):
    __tablename__ = "orders"
    __filterable_fields__ = ["status", "customer"]  # "customer" is a relationship


class Customer(BedrockModel):
    __tablename__ = "customers"
    __filterable_fields__ = ["name"]  # password_hash stays hidden
```

- Each hop of a dotted or colon path is checked against its own model: `customer.name` needs `customer` on `Order` and `name` on `Customer`.
- `count_pk` must be a primary key.
- Any other name raises `BadFilterFormatError` ("Field `x` is not filterable on Order"). Hidden and missing fields raise the same error, so clients cannot probe the schema.
- If the application already validates field names before they reach the query builder, set `__filterable_fields__ = "__all__"` to turn the check off for that model. Related models reached through a path still apply their own `__filterable_fields__`, so set `"__all__"` on them too if needed. With `"__all__"`, guarding secret columns is the application's job.
- `sqla_filters` and the `__searchable_columns__` used by `q` are written by your code and are not checked.

### Basic Usage

```python
from bedrock.database.service import search_filter_sort_paginate

result = search_filter_sort_paginate(
    db_session=db.session,
    model=Product,
    filter_specs=[
        {"field": "name", "op": "ilike", "value": "%widget%"},
    ],
    sort_key="name",
    sort_dir="asc",
    page=1,
    limit=20,
)

result["items"]     # List of Product instances
result["total"]     # Total count matching filters
result["page_info"] # Pagination metadata
```

### Async Sessions

In `async def` services, call `asearch_filter_sort_paginate` with `db.asession`. It takes the same arguments and returns the same dictionary:

```python
from bedrock.database.service import asearch_filter_sort_paginate

result = await asearch_filter_sort_paginate(
    db_session=db.asession,
    model=Product,
    filter_specs=[{"field": "name", "op": "ilike", "value": "%widget%"}],
    page=1,
    limit=20,
)
```

Async sessions cannot lazy-load relationships. Load the relationships you read on `result["items"]` through `options`, for example `options=[selectinload(Product.tags)]`.

### Boolean Combinators

Combine multiple filters with `or` and `and`:

```python
filter_specs = {
    "or": [
        {"field": "name", "op": "ilike", "value": "%widget%"},
        {"field": "price", "op": "<", "value": 100},
    ]
}

filter_specs = {
    "and": [
        {"field": "name", "op": "ilike", "value": "%widget%"},
        {"field": "price", "op": ">=", "value": 50},
    ]
}
```

### Sorting

Pass `sort_key` as a string or list of tuples:

```python
# Single sort
sort_key="name"
sort_dir="desc"

# Multiple sorts
sort_key=[("name", "asc"), ("price", "desc")]
```

### Pagination

Control results with `page`, `limit`, and `show_all`:

```python
result = search_filter_sort_paginate(
    db_session=db.session,
    model=Product,
    page=2,       # Second page
    limit=10,     # 10 items per page
)

# Or fetch everything
result = search_filter_sort_paginate(
    db_session=db.session,
    model=Product,
    show_all=True,
)
```

`limit` must be an integer from 1 to 1000, including when `show_all=True`; invalid values raise `InvalidQueryLimitError`.

The `page_info` dictionary includes:

| Key | Description |
|-----|-------------|
| `total` | Total matching records; with `group_by`, the number of groups |
| `limit` | Items per page |
| `offset` | Current offset |
| `page` | Current page number |
| `query` | Search string, or an empty string |
| `filters` | Supplied filter specifications, or an empty list |
| `has_more` | Whether more pages exist |
| `paginated` | Whether pagination is active |

### Related Model Filters

Filter across relationships using dot notation for joins or colon notation for `any()`/`has()`:

```python
# Dot notation: joins the related model
{"field": "category.name", "op": "eq", "value": "Electronics"}

# Colon notation: uses any() for collections, has() for scalars
{"field": "category:name", "op": "eq", "value": "Electronics"}
```

Both paths require `category` in `Product.__filterable_fields__` and `name` in the related model's `__filterable_fields__` (see [Filterable Fields](#filterable-fields)).

## Migrations

Bedrock runs migrations itself. Each app has its own set of migration scripts, identified by its import path, and executed migrations are recorded in the `bedrock_migrations` table with primary key `(app, revision)`. Scripts are executed and generated through Alembic's library API (operations and autogenerate); Alembic's command layer, `env.py`, branch labels, and `alembic_version` are not used. The `MigrationsManager` handles revision creation, dependency-aware upgrades and downgrades, installation, and adoption of legacy databases.

For the complete migration CLI reference, see [CLI Reference — Database Commands](/docs/guides/cli#database-commands-bedrock-db).

### Table Ownership

Autogeneration resolves ownership for every table in the shared metadata. Ordinary ORM models need no extra declaration: the model's defining Python package selects the longest matching loaded Bedrock module import path. Models in imported domain packages are included; importing or re-exporting another module's model does not transfer ownership. Import needed domain models from `models.py`; Bedrock does not discover unimported model files.

Unmapped `Table` objects, such as association tables, declare their owner through SQLAlchemy's `info` dictionary. For example, in `myapp.tags.models`, after the users module has defined `users` in the shared metadata:

```python
from sqlalchemy import Column, ForeignKey, Integer, String, Table
from bedrock.database import BedrockModel

user_labels = Table(
    "user_labels",
    BedrockModel.metadata,
    Column("user_id", Integer, ForeignKey("users.id"), primary_key=True),
    Column("label", String(50), primary_key=True),
    info={"bedrock_module": "myapp.tags"},
)
```

Declare `myapp.users` in the tags module's manifest `depends_on`. Cross-module foreign keys retain access to the complete metadata, but do not grant ownership of their referenced tables. Migration ordering between modules is recorded in the scripts' `depends_on` (see [Cross-Module Dependencies](#cross-module-dependencies)).

An ORM model may also declare `__table_args__ = {"info": {"bedrock_module": "myapp.tags"}}`; this must agree with its defining module. Missing ownership, invalid declarations, unloaded owners, owners without a `models` module, and conflicting mappings raise `MigrationError` before a revision is written. There is no fallback to all tables. Keep all mappings of one table in one module: same-module single-table inheritance is supported, cross-module single-table mappings are rejected, and joined-table inheritance assigns each local table separately.

Every mapped class sharing a table must resolve to an owner; one resolved class does not cover an unresolved class. A valid explicit table declaration can supply missing ownership, but cannot override a known conflict between loaded modules.

Ownership is a per-operation snapshot, not a database ownership table or a global registration hook. Table identities include schema; explicit and implicit default schemas refer to the same physical table, and duplicate declarations of that physical table are rejected. Reflection is restricted to the target's schemas and tables, and metadata objects are filtered too. An empty owned-table set creates no tables.

When a model is removed, the remaining database table's historical owner cannot be inferred. It is not automatically claimed or dropped: write a reviewed explicit migration with `bedrock db revision <app> -m "drop obsolete table" --no-autogenerate`. Historical upgrade/downgrade, manual revisions, and offline SQL rendering do not require a current ownership snapshot. Raw Alembic calls without Bedrock's managed context retain the full metadata view and are outside this isolation guarantee.

### Programmatic Usage

```python
from bedrock.module import apps
from bedrock.database import MigrationsManager

migrations = MigrationsManager(
    registry=apps,
    database_url=db.settings.SQLALCHEMY_DATABASE_URI,
)

# Create a new revision
migrations.revision("myapp.users", "add email column")

# Apply migrations
migrations.upgrade("myapp.users")

# Check current state
migrations.current("myapp.users")

# View history
history = migrations.get_history("myapp.users")
```

### Migration Scripts

Each module keeps its scripts in `<package_dir>/migrations/*.py`; files starting with `_` are skipped. A script declares a string `revision`, `down_revision` (a revision of the same module, or `None`), and optionally `depends_on`. The file stem is the revision name. `bedrock db revision` names new revisions `0001_initial`, `0002_add_email`, and so on: it takes the module's highest number plus one and a slug of the message (the full name is at most 64 characters). Existing random revision IDs are kept as they are; the next generated name continues the numbering and uses the old head as its `down_revision`. Revision names only need to be unique within a module, so two modules can each have `0001_initial`.

`branch_labels` is ignored, so scripts that still declare it keep loading. A script that never defines `revision`, a `down_revision` that is not a revision of the same module, a duplicate revision, or a dependency cycle raises `MigrationError`. A migration runs in its own transaction. SQLite runs DDL inside it; MySQL and MariaDB cannot roll back DDL, so after a failure compare the real schema with the version table before retrying. Scripts must not commit on their own or use `autocommit_block()`; review pending scripts for this before upgrading.

### Cross-Module Dependencies

`depends_on` lists qualified `app:revision` references, for example `("myapp.users:0002_email",)`. Bare revision names are rejected, and the target must belong to a module that is a direct manifest `depends_on` of the owner. Upgrading a module first applies every migration it depends on, in dependency order, and nothing else: unrelated modules and later revisions of a dependency stay untouched.

`bedrock db revision` writes these references for you. It records the heads of the modules that the new revision depends on, and repeats a reference only when that module has a newer head. Autogeneration requires the module to be at head (`bedrock db upgrade <app>` first); any generation requires a single head.

A generated revision is a reviewable draft: read it, edit it, and commit it with the module. At run time Bedrock uses only the dependency graph declared in the committed scripts (`down_revision` plus qualified `depends_on`). It never infers ordering from foreign keys, table names, or the current models, so add a `depends_on` entry by hand when a script needs another module's tables that generation did not record.

### Rolling Back

`downgrade` undoes a module's migrations in reverse dependency order. If other modules' applied migrations depend on them, the command stops with `MigrationError` naming those migrations and changes nothing. Pass `cascade=True` (`--cascade` on the CLI) to roll back the dependent modules first. Dependents that are not loaded are always an error, even with `cascade`: load those modules (`--load <app>` on the CLI) and roll them back first. Rolling back never touches unrelated modules, even when they use the same revision names.

To remove a module's schema from the CLI, use `bedrock db downgrade <app> base`; there is no `bedrock db uninstall` command. The Python `MigrationsManager.uninstall()` remains and is equivalent to downgrading the module to base.

### First Install

`ensure_schema()` runs the module's migration scripts up to head, together with the migrations they depend on, and returns `"created"` (first run for the module), `"upgraded"`, or `"up-to-date"`. It no longer creates tables from metadata with `create_all` and a stamp, so a module that has models but no migration scripts raises `MigrationError`: generate the initial migration first with `bedrock db revision <app> -m "initial schema"`.

Table ownership applies when a revision is generated. A successful installation now means the recorded scripts really ran, so a rollback executes the `downgrade()` of scripts whose `upgrade()` ran.

`bedrock app install <target>` calls `ensure_schema()` for the target only. The migration closure (the target's migrations plus the migrations they depend on in other modules) is applied either way; `--with-dependencies` additionally runs each dependency's own schema step and installation hooks, and `--skip-migrations` skips only the schema step.

### Adopting an Existing Database

Databases created by earlier Bedrock versions record migrations in Alembic's `alembic_version` table. Every migration command refuses to run on such a database until you adopt it once. Alembic's native CLI must no longer be used on Bedrock-managed databases.

1. Pause migration commands, and back up the database, the deployed package, and the original migration scripts. Record `alembic_version` and the actual schema and data of every environment.
2. Load every module that appears in `alembic_version` and run `bedrock db adopt <app> ...`. Each old head must belong to exactly one loaded module. Bedrock resolves it through that deployment's own revision graph; today's manifest edges are not evidence of what ran historically. If a head is missing, ambiguous, or its history cannot be resolved, nothing is written; fix the scripts or the loaded modules and retry.
3. `adopt` writes one `origin = 'baseline'` row for every revision up to those heads into a staging table, verifies it, and renames it atomically to `bedrock_migrations`. The old `alembic_version` table is left as an audit snapshot. A command that is interrupted before publishing leaves only staging state and can be retried; an already published table is never dropped or re-imported.
4. Baseline rows are protected. They mean "assumed to be in place", not "executed by Bedrock": their scripts are never replayed, and a downgrade or cascade that would need to undo a baseline row fails before the first DDL statement. Rolling back to the baseline itself is allowed. A suspected missed data migration needs manual reconciliation; adoption does not replay it.
5. After the new version has written to the database, do not switch back to the old program against the same data. Restore the matching database, program, and migration files together; never let old code reread `alembic_version`.

#### Before adoption: qualify references, preserve published history

Use the **actually deployed scripts**. Record all heads from `SELECT version_num FROM alembic_version` and locate each in its owner's `migrations/` directory. Stop on missing scripts or ambiguous owners. Do not renumber published random IDs to `0001_*`.

For example, suppose an orders script declares `revision = "c91a"`, `down_revision = "c900"` and `depends_on = "a12f"`. After verifying from the original release that `a12f` belongs to `myapp.auth`, change only the reference syntax in the new deployment copy:

```python
revision = "c91a"
down_revision = "c900"
depends_on = ("myapp.auth:a12f",)
```

Preserve `upgrade()`, `downgrade()`, local parent IDs and every parent of a merge. Existing `branch_labels` may stay; they do not establish ownership. `myapp.auth` must be a direct dependency in the orders manifest. Do not substitute today's upstream head for an unknown historical dependency or regenerate old scripts from current models. If the graph cannot be partitioned without changing its meaning, reconcile it manually; do not stamp or edit database rows to bypass validation.

On a restored database copy, exercise normal script loading, adopt, then verify the position:

```bash
bedrock db history myapp.orders
bedrock db adopt myapp.auth myapp.orders
bedrock db current myapp.orders
bedrock db check myapp.orders
```

Compare `current` with the original position for that module. `check` reporting `behind` is expected if the release contains pending scripts. Correct actual differences with new, unapplied migrations; do not replay the baseline. These steps import `alembic_version`; they are not an in-place upgrade procedure for an experimental Bedrock ledger.

#### Adding a new module registry after adoption

Use `adopt` for existing history. Use `init-ledger` only to add a genuinely new registry after adoption:

| Situation | Command |
|-----------|---------|
| Legacy database, nothing adopted yet | `bedrock db adopt <app> ...` |
| Adopted database, new revisions to apply | `bedrock db upgrade <app>` |
| Adopted database; independent modules with no prior migrations or business tables | `bedrock db init-ledger <root> [<root> ...] --adopted-ledger <source-name>` |

```bash
export DATABASE_MIGRATION_VERSION_TABLE=billing_migrations
bedrock db init-ledger myapp.billing --adopted-ledger bedrock_migrations
```

Programmatic equivalent: `mgr.init_ledger(adopted_ledger="bedrock_migrations")` on a manager built with the new registry and the target `version_table`. It returns `None`.

`init-ledger` creates an empty target ledger. It neither imports baseline rows nor executes migrations; ordinary `upgrade` still refuses to initialize beside legacy history. The operator must verify there is no prior handwritten schema or unrecorded data migration.

Preflight, in order:

1. Pause migration commands and take a verified backup of the database, the deployed package, and the migration scripts.
2. Confirm the source ledger was published by `adopt` and covers the core legacy heads; the new modules must be disjoint.
3. Load exactly the new registry's modules and rehearse on a restored copy.

It refuses, writing nothing, when any of the following holds:

- the legacy `alembic_version` table is missing, or the source ledger is not a valid adopted ledger with evidence for the old heads;
- the source ledger already has rows for a loaded module;
- a table owned by a loaded module's models already exists in the database;
- the target ledger, or a staging table of the source or target, already exists.

Fix the reported cause and rerun; never create or edit ledger rows by hand to get past a refusal.

### Squashing migrations

Prepare and rehearse in development. A squash replaces a linear range, not a schema diff. Reviewing transaction boundaries matters: one new script runs as one migration, not three. Only use trusted module hooks and migration imports; they can have side effects.

1. Generate the candidate outside the active migrations directories. Review it, then replace all listed old files together. Replay the old and new paths against equivalent seeded databases: compare rows, indexes, constraints, and downgrade behavior. Unloaded and unapplied third-party plugins cannot be checked.
2. Publish the bridge release with the old scripts. For a squash of `0002_add` through `0004_finalize`, partially applied databases must first reach `0004_finalize` on the old release; upgrade refuses a partial or conflicting range. Keeping its ID preserves dependents such as `0005_ship`.
3. Deploy the new code and run the ordinary upgrade (`bedrock db upgrade`, or `ensure_schema` at startup). Complete approved ranges in the target's ancestry are reconciled before business migrations without replay: a fresh database executes the replacement, a current one skips it. Read-only commands never mutate. For a handover or recovery, pause writes and migration/install jobs, back up, then use `bedrock db squash apply` to preview and `--apply` to switch manually, confirming the database, ledger and affected rows first.

Retired IDs remain reserved when generating later revisions. Do not use `head` or `base` as rename targets. Adopt ambiguous bare Alembic revisions on the bridge release. Manual replacements need synchronous, non-generic `upgrade()` and `downgrade()` functions.

A failed business migration on MySQL or MariaDB may already have committed DDL: inspect the schema before retrying. Retrying a ledger switch is different. Restoring old history requires matching code, scripts and a backup; after business writes resume, an old backup alone loses new data.

### Existing Migration Safety

Bedrock does not rewrite already generated scripts. Before upgrading or rolling back an affected module:

1. Pause these operations, back up the database and migration files, and record both `alembic_version` (or `bedrock_migrations`) and the actual schema/data state in every deployed environment.
2. Review both `upgrade()` and `downgrade()` in core and plugin modules, including tables, columns, indexes, constraints, and raw SQL. A script declaring the right module is not evidence of safe table operations, and autogeneration filters are not a script execution sandbox.
3. Regenerate or correct an unpublished revision only after confirming no environment has applied it. For published or applied revisions, coordinate a reviewed repair across deployments; do not casually delete revisions or change their names. A new revision alone cannot neutralize a dangerous older downgrade that a rollback will still reach.
4. After a failed upgrade, inspect residual DDL even if no revision was recorded. If data was already deleted, restore it through verified backups or database recovery; recreating tables does not restore rows.
5. Verify the actual install/upgrade/downgrade paths on an isolated copy of production data before resuming operations.

### Migration Lock

`upgrade` and `downgrade`, including `ensure_schema()` and `uninstall()`, take a database lock so two processes do not migrate the same database together.

| Dialect | Lock | Wait |
|---------|------|------|
| PostgreSQL | `pg_try_advisory_lock` | Polled until `DATABASE_MIGRATION_LOCK_TIMEOUT` (default 30 seconds) |
| MySQL, MariaDB | `GET_LOCK` | Same timeout, rounded up to whole seconds |
| SQLite | none | Run migrations from a single process |

A timeout raises `MigrationError`. SQLite has no shared lock in this manager.

### Custom Version Table and Independent Module Sets

The version table defaults to `bedrock_migrations`. `MigrationsManager(..., version_table="...")` and the host setting `DATABASE_MIGRATION_VERSION_TABLE` change it. The name must be a lowercase simple SQL identifier (`[a-z_][a-z0-9_]*`) of at most 57 characters. The name itself and `<name>_adopt` (the adopt staging table) are reserved, and a name must not end in `_adopt`.

Programmatic code may run several independent registries against one database, each with its own ledger:

```python
from bedrock.database import MigrationsManager
from bedrock.module.registry import ModuleRegistry

billing, search = ModuleRegistry(), ModuleRegistry()
billing.populate(["myproject.modules.billing"])
search.populate(["myproject.modules.search"])

url = "postgresql://user:pass@localhost/mydb"
MigrationsManager(billing, url, version_table="billing_migrations").ensure_schema("myproject.modules.billing")
MigrationsManager(search, url, version_table="search_migrations").ensure_schema("myproject.modules.search")
```

Rules:

- The module sets must be independent: their model tables are disjoint and no migration depends on a module in another ledger. Bedrock does not check this across ledgers.
- All managers on one database share the same migration lock, so they serialize against each other.
- The host application and the `bedrock` CLI use a single configured root set and one ledger, chosen by `DATABASE_MIGRATION_VERSION_TABLE`. There is no CLI flag or manifest field for it.
  ```bash
  DATABASE_MIGRATION_VERSION_TABLE=billing_migrations bedrock db upgrade myproject.modules.billing
  ```
- Never rename a table to switch ledgers. Changing the name points Bedrock at a different (possibly empty) ledger, so already-applied migrations look pending.
- `adopt` imports the *whole* legacy `alembic_version` baseline into the configured ledger, so adopt with every module loaded. A module set that owns only part of the legacy history cannot adopt it.


### `bedrock db check`

`bedrock db check <app>` prints the current and head revisions for the app and for every other installed app that already has migration scripts. It does not change the database and does not create the `bedrock_migrations` table. The process exits with status 1 when any reported module is `behind` or `unknown`. `unknown` includes a database that has never been migrated. Use the command as a deploy gate before serving traffic. See [CLI Reference — Database Commands](/docs/guides/cli#database-commands-bedrock-db).

## Model Events

Bedrock does not wrap ORM events. Register SQLAlchemy listeners directly and pick the phase you need:

```python
from sqlalchemy import event
from sqlalchemy.orm import Session

# After the INSERT ran: the primary key is set. Use `connection` for extra SQL; do not modify the session.
@event.listens_for(Catalog, "after_insert", propagate=True)
def catalog_inserted(mapper, connection, target):
    ...

# Before the flush: objects added to the session here are flushed in the same transaction.
@event.listens_for(Session, "before_flush")
def audit_catalog(session, flush_context, instances):
    for obj in session.new:
        if isinstance(obj, Catalog):
            session.add(AuditLog(action="catalog_created"))
```

`after_update` / `after_delete` (and the `before_*` variants) work the same way. `propagate=True` also covers subclasses. See SQLAlchemy's [ORM events](https://docs.sqlalchemy.org/en/20/orm/events.html) for every hook and its restrictions.

## Architecture

The database module is organized into focused files:

```
bedrock/database/
├── __init__.py            # Public exports
├── base.py                # BedrockModel (DeclarativeBase + CrudMixin)
├── config.py              # DbSettings (env-prefixed BaseSettings)
├── connection.py          # Engine and session factory builders
├── filters.py             # Filter operators and boolean combinators
├── manager.py             # DatabaseManager singleton (db)
├── migration/             # Module migration manager, graph, ledger and script writer
├── service.py             # search_filter_sort_paginate query builder
├── session_factory.py     # Context-local sessions via ContextVar
└── utils.py               # Model registry helpers
```

## Anti-Patterns

**Avoid reinitializing `db` during active work.** `db.init()` supports replacement: it constructs the new synchronous engine first, then clears the current context's synchronous session and disposes the previous synchronous engine. If an async engine has already opened a connection, `await db.aclose()` before `init()` so those connections close on the event loop. Other contexts must manage their own sessions before replacement.

**Don't access `db.session` before initialization.** This raises `DatabaseNotConfiguredError`. Always call `db.init()` first.

**Don't read `db.session` outside a scope.** It raises `SessionNotBoundError`. Bind a session at the entry point with `db.session_scope()` or the FastAPI middleware; services only read it.

**Don't forget to clear sessions you bind yourself.** A session bound with `db.set_session()` stays bound until `db.clear_session()`. Call it in a `finally` block.

**Don't put HTTP types in service or model layers.** Request and Response objects belong at adapter boundaries, not in business logic.

**Don't bypass `ModuleRegistry.install()` for migrations.** The registry handles dependency ordering and lifecycle hooks. Manual module loading skips these.

**Don't hardcode database URLs.** Use environment variables or `DbSettings` so configuration stays external to code.

**Don't instantiate settings eagerly at module level if env vars may not be ready.** Wrap module-level singletons with `SettingsProxy` from `bedrock.conf` to defer initialization.

**Don't import `contrib` modules from core code.** The core runtime must not depend on contrib packages.
