Bedrock ships with a SQLAlchemy 2.0 database layer that handles engine setup, context-local sessions, declarative models, and Alembic migrations. The whole subsystem lives under `bedrock.database`.

## Quick Start

Define a model, initialize the database, and start querying:

```python
from bedrock.database import db, BedrockModel
from sqlalchemy import Column, String, Integer

class Product(BedrockModel):
    __tablename__ = "products"

    id = Column(Integer, primary_key=True)
    name = Column(String(100), nullable=False)

# Initialize once at process start
db.init()

# Use the context-local session
with db.session as session:
    product = Product(name="Widget")
    session.add(product)
    session.commit()

    # Query back
    all_products = session.query(Product).all()
```

That's the core loop. The rest of this page covers configuration, the full API, and advanced patterns.

## Configuration

Database settings use environment variables with the `DATABASE_` prefix. `DbSettings` is a Pydantic `BaseSettings` subclass, so it reads from the environment automatically.

### Environment Variables

| Variable | Type | Default | Description |
|----------|------|---------|-------------|
| `DATABASE_TYPE` | `str` | `"sqlite"` | Database dialect (`sqlite`, `postgresql`, `mysql`) |
| `DATABASE_DRIVER` | `str` | `"pysqlite"` | DBAPI driver (`pysqlite`, `psycopg2`, `pymysql`) |
| `DATABASE_HOST` | `str \| None` | `None` | Database host (required for non-SQLite) |
| `DATABASE_PORT` | `int \| None` | `None` | Database port (required for non-SQLite) |
| `DATABASE_USERNAME` | `str \| None` | `None` | Database username |
| `DATABASE_PASSWORD` | `str \| None` | `None` | Database password |
| `DATABASE_MAX_CONNECTIONS` | `int` | `10` | Maximum connection pool size |
| `DATABASE_POOL_TIMEOUT` | `int` | `30` | Seconds to wait for a connection |
| `DATABASE_POOL_SIZE` | `int` | `10` | Number of connections to maintain |
| `DATABASE_POOL_RECYCLE` | `int` | `1800` | Seconds before recycling a connection |
| `DATABASE_SCHEMA` | `str` | `"bedrock.db"` | Database name or file path |

### SQLite

```bash
export DATABASE_TYPE=sqlite
export DATABASE_DRIVER=pysqlite
export DATABASE_SCHEMA=bedrock.db
```

For in-memory databases, set `DATABASE_SCHEMA=:memory:`.

### PostgreSQL

```bash
export DATABASE_TYPE=postgresql
export DATABASE_DRIVER=psycopg2
export DATABASE_HOST=localhost
export DATABASE_PORT=5432
export DATABASE_USERNAME=myuser
export DATABASE_PASSWORD=mypassword
export DATABASE_SCHEMA=myapp
```

### MySQL

```bash
export DATABASE_TYPE=mysql
export DATABASE_DRIVER=pymysql
export DATABASE_HOST=localhost
export DATABASE_PORT=3306
export DATABASE_USERNAME=root
export DATABASE_PASSWORD=secret
export DATABASE_SCHEMA=myapp
```

### Programmatic Configuration

Pass a `DbSettings` instance directly to `db.init()`:

```python
from bedrock.database import db, DbSettings

settings = DbSettings(
    TYPE="postgresql",
    DRIVER="psycopg2",
    HOST="localhost",
    PORT=5432,
    USERNAME="admin",
    PASSWORD="secret",
    SCHEMA="myapp",
)

db.init(settings=settings)
```

You can also override the connection URL entirely:

```python
db.init(url="postgresql+psycopg2://admin:secret@localhost:5432/myapp")
```

## DatabaseManager

The `db` singleton is a `DatabaseManager` instance. It owns the engine, session factory, and settings. All access goes through this object.

### API Reference

| Method / Property | Signature | Description |
|-------------------|-----------|-------------|
| `db.init()` | `init(url: str \| None = None, settings: DbSettings \| None = None)` | Initialize engine and session factory. Call once at process start. |
| `db.engine` | `property → Engine` | The SQLAlchemy engine. Raises `DatabaseNotConfiguredError` if not initialized. |
| `db.session` | `property → Session` | The current context-local session. Creates one on first access within a context. |
| `db.session_factory` | `property → SessionFactory` | The underlying session factory. |
| `db.settings` | `property → DbSettings` | The resolved database settings. |
| `db.set_session(session)` | `set_session(session: Session)` | Bind an existing session to the current execution context. |
| `db.clear_session()` | `clear_session()` | Clear the current context-local session binding. |

### Error Handling

Accessing `db.engine`, `db.session`, or `db.settings` before calling `db.init()` raises `DatabaseNotConfiguredError`. Always initialize the database before using any of these properties.

## Session Management

Bedrock uses context-local sessions backed by a `ContextVar`. Each execution context (thread, async task, request) gets its own session automatically.

### How It Works

The `SessionFactory` wraps SQLAlchemy's `sessionmaker`. When you access `db.session`, it checks the `ContextVar` for an existing session. If none exists, it creates one and stores it. Subsequent accesses within the same context return the same session.

```python
from bedrock.database import db

db.init()

# First access creates a session
session = db.session
session.add(Product(name="Widget"))
session.commit()

# Same session within the same context
same_session = db.session
assert session is same_session
```

### Binding an External Session

When working with frameworks that manage their own sessions (like FastAPI's dependency injection), you can bind an existing session:

```python
from bedrock.database import db

# Bind a session from an external source
db.set_session(framework_session)

# Now db.session returns the bound session
product = db.session.query(Product).first()

# Clean up when done
db.clear_session()
```

### Clearing Sessions

Always clear sessions when a request or task finishes to prevent stale data:

```python
from bedrock.database import db

try:
    # Process request...
    result = db.session.query(Product).all()
finally:
    db.clear_session()
```

## BedrockModel

All Bedrock models extend `BedrockModel`, which combines SQLAlchemy's `DeclarativeBase` with a `CrudMixin` for common operations.

### Built-in Methods

| Method / Property | Description |
|-------------------|-------------|
| `.dict()` | Returns a dictionary of all column values |
| `.update(**kwargs)` | Sets attributes from keyword arguments |
| `.delete()` | Deletes the instance from its session |
| `.verbose_name` | Returns the class name as a human-readable label |
| `.__repr__()` | Returns `<ClassName #id>` format |

### Example

```python
from bedrock.database import BedrockModel
from sqlalchemy import Column, String, Integer

class Product(BedrockModel):
    __tablename__ = "products"

    id = Column(Integer, primary_key=True)
    name = Column(String(100), nullable=False)
    price = Column(Integer, default=0)

# Create and use
product = Product(name="Widget", price=999)
product.dict()  # {"id": None, "name": "Widget", "price": 999}

# Update attributes
product.update(price=1499)

# Delete (must be attached to a session)
session.add(product)
session.commit()
product.delete()
session.commit()
```

### Default Values

BedrockModel listens for the `init` event and applies column defaults before the constructor finishes. Callable defaults are invoked with the instance as an argument. This means default values are set consistently, even when you pass explicit kwargs.

## Query Builder

The `search_filter_sort_paginate` function builds queries with filtering, sorting, pagination, and automatic joins. It returns a dictionary with `items`, `total`, and `page_info`.

### Basic Usage

```python
from bedrock.database.service import search_filter_sort_paginate

result = search_filter_sort_paginate(
    db_session=db.session,
    model=Product,
    filter_specs=[
        {"field": "name", "op": "ilike", "value": "%widget%"},
    ],
    sort_key="name",
    sort_dir="asc",
    page=1,
    limit=20,
)

result["items"]     # List of Product instances
result["total"]     # Total count matching filters
result["page_info"] # Pagination metadata
```

### Filter Operators

| Operator | Symbol | Description |
|----------|--------|-------------|
| Equal | `==`, `eq` | Exact match |
| Not equal | `!=`, `neq` | Inequality |
| Greater than | `>`, `gt` | Strictly greater |
| Less than | `<`, `lt` | Strictly less |
| Greater or equal | `>=`, `ge` | Greater or equal |
| Less or equal | `<=`, `le` | Less or equal |
| Like | `like` | SQL LIKE pattern match |
| Case-insensitive like | `ilike` | Case-insensitive LIKE |
| Not ilike | `not_ilike` | Negated case-insensitive LIKE |
| In | `in` | Value in list |
| Not in | `not_in` | Value not in list |
| Between | `between` | Value between two bounds |
| Is null | `is_null` | Column is NULL |
| Not null | `is_not_null` | Column is not NULL |
| Any | `any` | Relationship has any matching related object |
| Not any | `not_any` | Negated any |
| Has | `has` | Scalar relationship matches |
| Text search | `text_search` | Full-text search on related model |
| Fuzzy search | `fuzzy_search` | Case-insensitive substring match |

### Boolean Combinators

Combine multiple filters with `or` and `and`:

```python
filter_specs = {
    "or": [
        {"field": "name", "op": "ilike", "value": "%widget%"},
        {"field": "price", "op": "<", "value": 100},
    ]
}

filter_specs = {
    "and": [
        {"field": "name", "op": "ilike", "value": "%widget%"},
        {"field": "price", "op": ">=", "value": 50},
    ]
}
```

### Sorting

Pass `sort_key` as a string or list of tuples:

```python
# Single sort
sort_key="name"
sort_dir="desc"

# Multiple sorts
sort_key=[("name", "asc"), ("price", "desc")]
```

### Pagination

Control results with `page`, `limit`, and `show_all`:

```python
result = search_filter_sort_paginate(
    db_session=db.session,
    model=Product,
    page=2,       # Second page
    limit=10,     # 10 items per page
)

# Or fetch everything
result = search_filter_sort_paginate(
    db_session=db.session,
    model=Product,
    show_all=True,
)
```

The `page_info` dictionary includes:

| Key | Description |
|-----|-------------|
| `total` | Total matching records |
| `limit` | Items per page |
| `offset` | Current offset |
| `page` | Current page number |
| `has_more` | Whether more pages exist |
| `paginated` | Whether pagination is active |

### Related Model Filters

Filter across relationships using dot notation for joins or colon notation for `any()`/`has()`:

```python
# Dot notation: joins the related model
{"field": "category.name", "op": "eq", "value": "Electronics"}

# Colon notation: uses any() for collections, has() for scalars
{"field": "category:name", "op": "eq", "value": "Electronics"}
```

## Migrations

Bedrock wraps Alembic with per-module branching. Each app gets its own Alembic branch, identified by its import path. The `MigrationsManager` handles revision creation, upgrades, downgrades, and schema stamping.

For the complete migration CLI reference, see [CLI Reference — Database Commands](/docs/guides/cli#database-commands-bedrock-db).

### Programmatic Usage

```python
from bedrock.database.migrations_manager import MigrationsManager

migrations = MigrationsManager(
    registry=apps,
    database_url=db.settings.SQLALCHEMY_DATABASE_URI,
)

# Create a new revision
migrations.revision("myapp.users", "add email column")

# Apply migrations
migrations.upgrade("myapp.users")

# Check current state
migrations.current("myapp.users")

# View history
history = migrations.get_history("myapp.users")
```

### Branch Ownership

Each app's migrations directory is audited before operations. If a revision file declares a branch label that doesn't match the app's import path, a `BranchOwnershipError` is raised. This prevents cross-app version-tree pollution.

### First Install

When an app has no existing revisions, `ensure_schema()` creates all tables from SQLAlchemy metadata and stamps the branch at head. This avoids running migration scripts for brand-new apps.

## Model Observer

The observer system hooks into SQLAlchemy's `before_flush` event to invoke callbacks when models are inserted, updated, or deleted.

### Event Identifiers

| Identifier | Fires When |
|------------|------------|
| `on_insert` | A new instance is added to the session |
| `on_update` | An existing instance is modified |
| `on_delete` | An instance is marked for deletion |

### Registering Observers

Use the `@observes_model` decorator:

```python
from bedrock.database import BedrockModel
from bedrock.database.observer import observes_model, observer
from sqlalchemy import Column, Integer, String

class Catalog(BedrockModel):
    __tablename__ = "catalog"
    id = Column(Integer, primary_key=True)
    name = Column(String(100))

@observes_model(Catalog, "on_insert", "on_delete")
def log_catalog_changes(session, target, identifier):
    print(f"Catalog {target.id} was {identifier}")
```

The callback receives three arguments: the session, the model instance, and the event identifier string.

### Custom Observer Instances

Pass a custom `ModelObserver` via the `observer` keyword:

```python
from bedrock.database.observer import ModelObserver

custom_observer = ModelObserver()

@observes_model(Catalog, "on_insert", observer=custom_observer)
def handle_insert(session, target, identifier):
    # Only fires on the custom observer
    pass
```

### Weak References

Observer callbacks are stored as weak references. Bound methods use a `WeakMethod` wrapper to prevent memory leaks. If the object owning a bound method is garbage collected, the callback is silently skipped.

## Architecture

The database module is organized into focused files:

```
bedrock/database/
├── __init__.py            # Public exports
├── base.py                # BedrockModel (DeclarativeBase + CrudMixin)
├── config.py              # DbSettings (env-prefixed BaseSettings)
├── connection.py          # Engine and session factory builders
├── filters.py             # Filter operators and boolean combinators
├── manager.py             # DatabaseManager singleton (db)
├── migrations/            # Alembic env.py and script.py.mako
├── migrations_manager.py  # Per-module Alembic orchestration
├── observer.py            # Model lifecycle observer
├── service.py             # search_filter_sort_paginate query builder
├── session_factory.py     # Context-local sessions via ContextVar
└── utils.py               # Model registry helpers
```

## Anti-Patterns

**Don't call `db.init()` more than once.** The engine and session factory are not idempotent in all paths. Initialize once at process start.

**Don't access `db.session` before initialization.** This raises `DatabaseNotConfiguredError`. Always call `db.init()` first.

**Don't forget to clear sessions.** Stale sessions hold database connections and can return outdated data. Use `db.clear_session()` at the end of each request or task.

**Don't put HTTP types in service or model layers.** Request and Response objects belong at adapter boundaries, not in business logic.

**Don't bypass `ModuleRegistry.install()` for migrations.** The registry handles dependency ordering and lifecycle hooks. Manual module loading skips these.

**Don't hardcode database URLs.** Use environment variables or `DbSettings` so configuration stays external to code.

**Don't use `BaseSettings` directly for new settings.** Extend `LazySettings` to preserve deferred initialization.

**Don't import `contrib` modules from core code.** The core runtime must not depend on contrib packages.
