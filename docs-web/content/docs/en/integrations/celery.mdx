`bedrock-celery` connects Celery workers to the Bedrock runtime. Your project still creates and owns the Celery app; the package adds building blocks you can use independently:

| Component | What it does |
| --- | --- |
| `connect_worker(app)` | Runs `bedrock.setup()` in each worker process (after the fork, with the prefork pool) and `bedrock.shutdown()` when the process exits |
| `BedrockTask` | Gives each task its own DI scope and database session, and rolls back whatever is left uncommitted when it ends |
| `async def` tasks | Run with [`bedrock.run_async()`](/docs/guides/module-anatomy#calling-async-code-from-synchronous-code) on Bedrock's runtime loop with `db.asession`, sharing the async clients your lifecycle hooks opened |

<Callout type="info">
  `bedrock-celery` is not on PyPI yet. Until its first release, install it from GitHub:
  `uv add "bedrock-celery @ git+https://github.com/maacck/bedrock-py#subdirectory=integrations/celery"`.
</Callout>

`bedrock-celery` requires Python 3.12+ and installs `bedrock-core` and Celery 5.3+. Install your broker's extra yourself, for example `celery[redis]`. To use async tasks with a database, also install an async driver, for example `bedrock-core[async-postgresql]`.

## Project layout

Celery code stays outside your Bedrock modules, in the worker adapter described in [Module Anatomy](/docs/guides/module-anatomy). A module does not import Celery, and tasks only translate arguments and call services.

```text
src/shop/
├── inventory/                 # Bedrock module: no Celery code
│   ├── manifest.yaml
│   ├── models.py
│   ├── exc.py
│   └── service.py
└── adapters/
    └── worker/
        ├── app.py             # creates the Celery app
        └── inventory/
            └── tasks.py       # tasks: arguments -> service call -> result
```

## Create the app

```python
# shop/adapters/worker/app.py
from bedrock.database import db
from bedrock_celery import BedrockTask, connect_worker
from celery import Celery

app = Celery(
    "shop",
    broker="redis://localhost:6379/0",
    task_cls=BedrockTask,
    include=["shop.adapters.worker.inventory.tasks"],
)
db.init()  # builds the engine only; no connection is opened before the fork
connect_worker("shop.inventory")
```

- `task_cls=BedrockTask` makes every task of this app a `BedrockTask`. To opt in task by task instead, pass `base=BedrockTask` to `@app.task`.
- `connect_worker("shop.inventory")` names the root module, like `bedrock.setup()`. Without an argument it reads `BEDROCK_APP`.
- `db.init()` reads the `DATABASE_*` environment variables (see [Database](/docs/guides/database)). It is safe at import time because it does not connect. Do not run queries, or call `bedrock.setup()`, when the module is imported: with the prefork pool that happens in the parent process, and the children would share its connections.

## Write tasks

```python
# shop/adapters/worker/inventory/tasks.py
from shop.inventory.service import inventory_service

from ..app import app


@app.task
def restock(sku: str, quantity: int) -> int:
    return inventory_service.restock(sku, quantity)


@app.task(bind=True, max_retries=3)
async def arestock(self, sku: str, quantity: int) -> int:
    return await inventory_service.arestock(sku, quantity)
```

The service owns the transaction and commits, exactly as it does behind HTTP or in a CLI command:

```python
# shop/inventory/service.py
from bedrock.database import db
from sqlalchemy import select

from .exc import ItemNotFound
from .models import ItemModel


class InventoryService:
    def restock(self, sku: str, quantity: int) -> int:
        item = db.session.scalar(select(ItemModel).where(ItemModel.sku == sku))
        if item is None:
            raise ItemNotFound()
        item.stock += quantity
        stock = item.stock
        db.session.commit()
        return stock

    async def arestock(self, sku: str, quantity: int) -> int:
        item = await db.asession.scalar(select(ItemModel).where(ItemModel.sku == sku))
        if item is None:
            raise ItemNotFound()
        item.stock += quantity
        stock = item.stock  # read before commit: commit expires loaded attributes
        await db.asession.commit()
        return stock


inventory_service = InventoryService()
```

## Run it

```bash
export DATABASE_TYPE=postgresql DATABASE_HOST=localhost DATABASE_PORT=5432  # see the Database guide
celery -A shop.adapters.worker.app worker --pool prefork
```

A task that raises, such as `ItemNotFound`, fails like any Celery task: the exception is stored as the result and logged by the worker, and whatever the task did not commit is rolled back.

## Worker lifecycle

`connect_worker()` connects four Celery signals:

| Pool | Bedrock is set up | Bedrock is shut down |
| --- | --- | --- |
| `prefork` (default) | In every child process, after it starts (`worker_process_init`); never in the parent | When that child exits (`worker_process_shutdown`) |
| `solo`, `threads`, `gevent`, `eventlet` | Once in the worker process (`worker_init`) | When the worker stops (`worker_shutdown`) |

Hooks run exactly as under a plain `bedrock.setup()`: synchronous hooks in the thread that sets Bedrock up, async hooks on Bedrock's runtime loop. Async tasks use that same loop through `bedrock.run_async()`, so an async client opened by a hook is usable from tasks. `bedrock.shutdown()` also closes the database engines and the runtime loop. A child replaced because of `worker_max_tasks_per_child` sets Bedrock up again.

Call `connect_worker()` once, in the module that creates the Celery app. It does not configure logging; call `bedrock.logging.configure_logging()` there if you want Bedrock's sink.

## Tasks, scopes, and database sessions

`BedrockTask` runs each task inside `container.scope("task")`. A service registered with `Lifetime.SCOPED` resolves to one instance per task, and its `close()` method, if it has one, runs when the task ends.

A `def` task runs inside `db.session_scope()`; an `async def` task runs inside `db.asession_scope()`. Services own their transactions: they work in `db.session` / `db.asession` and commit. The task never commits for them; whatever is still uncommitted when it ends, for example because a service raised before committing, is rolled back.

- **Do not open `db.session_scope()` or `db.asession_scope()` in a service.** A session is already bound inside a task, so they raise `RuntimeError`. For the same reason, do not call another task directly (`other_task(...)`) from inside a task; send it with `.delay()` / `.apply_async()`, or call its service.
- **Each commit is final.** If a task retries after a service committed, the committed work stays. Keep writes that must succeed or fail together in one service method that commits once, and make tasks safe to run again.
- **A write nobody commits is lost.** The task still finishes successfully.
- **Side transactions** that must not share the task's transaction use `db.independent_session()` / `db.aindependent_session()`.
- If `db.init()` was not called in the worker, every `BedrockTask` fails with `DatabaseNotConfiguredError`. The first async task builds the async engine and requires `DATABASE_ASYNC_DRIVER`.

## Async tasks

Declare a task with `async def` to call async services. Celery runs tasks synchronously, so `BedrockTask` runs the coroutine to completion with `bedrock.run_async()` within the call: `self.request`, `self.retry()`, and the other task options work as in a `def` task. A `def` task can also call `bedrock.run_async()` itself for a single async call.

- **Async work in one process runs one task at a time.** The runtime loop has no thread of its own; the task's thread drives it. With the `threads` pool, async tasks from several threads take turns on the loop, while `def` tasks still run concurrently. Async tasks are tested with the `prefork`, `solo`, and `threads` pools.
- An async task binds only `db.asession`. Use async services in it, not services that use `db.session`.
- Do not call `asyncio.run()` in a task: it creates and closes a loop per call, and async engines and clients belong to the loop they were created on. Use `bedrock.run_async()`.

## Testing

Tasks can run eagerly with `task.apply()`. `def` tasks only need `db.init()`. Async tasks also work without setup; set Bedrock up when they rely on clients that `on_load` hooks open:

```python
import bedrock
import pytest

from shop.adapters.worker.inventory.tasks import arestock


@pytest.fixture
def bedrock_app():
    bedrock.setup("shop.inventory")
    yield
    bedrock.shutdown()  # also closes the database engines and the runtime loop


def test_arestock(bedrock_app):
    assert arestock.apply(args=("A1", 3)).get() == 3
```

## API reference

| Name | Signature | Notes |
| --- | --- | --- |
| `connect_worker` | `connect_worker(app: str \| None = None) -> None` | Connects the worker signals; call once where the Celery app is created |
| `BedrockTask` | `Celery(..., task_cls=BedrockTask)` or `@app.task(base=BedrockTask)` | DI scope and database session per task; runs `async def` tasks with `bedrock.run_async()` |

The package does not provide task discovery, beat schedules, retry policies, or exception mapping: those stay in your application.
